**库存基本公式（直接采纳）**：

```text
理论期末 = 有效期初 + 收货 + 调拨入 − 调拨出 − 报损 − Σ(销售 SKU × BOM 用量)
```

**数据边界（与门店实情核对）**：

- 门店：6 家 / 商品：18 个 SKU / 物料：20 项
- 安全库存：仅 STORE001 的牛奶 / 糖浆 / 杯子 / 茶叶 4 项
- 品牌真实 BOM：6 个 Brown Sugar Boba Milk Tea SKU，每个 9 条飞书配方，合计 54 条
- MVP Mock：其余 12 个商品；明确**不会编造**正式配方（待品牌补齐）
- 待品牌确认：半成品奶茶 / 黑糖成品 / 黑糖冻的出成率、合理损耗率与保质期

### 1.3 吸收建议

**可直接照搬的（已验证、低风险）**：

- **公式与硬规则定调**：库存公式 + D2/D1/S1/T2 四类硬规则 + 不调用 LLM 自动定责——作为 ABC 推送时 LLM 的"参考规则"，而非 LLM 自己下结论
- **分层持久化与"飞书仅只读"**：Base 持续作为只读来源 + R2 风格本地快照作兜底；不回写原始销售表 / BOM 表
- **Knowhow 用 R2 文本 + MVP 提炼版**：RAG 不一定要上向量库；规则提炼版与原文并存，便于审计与回归
- **加盟商"无前置审批"流程**：报损 / 调拨由门店自主，总部只后置查看 / 追溯 / 异常跟进；可平移到 ABC 推送体系
- **写入前确认机制**：门店助手写库存 / 报损前必须人工确认；这一约束纳入 Skill 设计

**需要扩展与补强的**：

- **研判档位 4 档 → 5 档**：在"有证据 / 已排除 / 疑似"基础上加"证据不足"（无收货记录场景）和"待盘点"（首日基线缺失）——归因表与工单状态需同步改
- **物料行业分层（6 类）**：包装耗材 / 易耗液体 / 现制半成品 / 自然损耗 / 称重原料 / 一般物料采用不同盘点容差与必查证据；与现有"现做茶饮专项"融合
- **跨营业日快照 + 期初回算**：每日 22:30 物耗日算改用"昨日固化的日结快照"作为期初；当前架构是"今天有销售后优先用昨日快照"，可与 22:30/23:00 节奏融合
- **ABC + 闭环**：A 日报（10:00）/ B 周报（周一 9:00）/ C 告警（实时 + 12:00/18:00）；加盟商反馈形成闭环（误判关闭 / 凭证上传 / 重派研判）
- **对话式门店助手入口**：ABC 现有单向推送，加一条"加盟商主动提问 / 多轮对话"通道（私聊 + SaaS HTML）；现有 P2P 私聊能力可直接接入

**与现有系统的接口对齐**：

- Base 7 表字段命名（采购单位 + 基本换算系数）已与 Demo 一致；只需补"每日盘点 / 按需盘点"标记
- 门店库存流水的 4 选单据类型（入库 / 消耗 / 报损 / 调拨）与 Demo 单据一一对应；可考虑加"状态"字段支持撤销
- 物料主数据 4 条（小茶日记 mock）+ 9 条 MOMOYO 真实物料需逐步统一行业分类标签（6 类）
- 现有 11 条规则 + 现做茶饮专项 + 6 类根因 + 4 档归因 → 升级为 5 档 + 6 类物料差异化容差

<callout emoji="💡">
**未决项**（待 user 拍板）：
- **6 类物料行业分类**：是否照搬（包装耗材 / 易耗液体 / 现制半成品 / 自然损耗 / 称重原料 / 一般物料），还是按 MOMOYO 茶饮业态简化？
- **5 档研判输出**：现有 4 档是否升级？升级后归因表与工单状态需同步改
- **RAG 形态**：直接采用 R2 文本 + MVP 提炼版（已验证），还是尝试向量库（功能更强 / 成本与维护更高）？
- **对话式入口**：私聊 vs SaaS HTML 哪个优先？MOMOYO 印尼加盟商英文 / 印尼语为主，需要多语言支持
</callout>

## 二、双轨推送架构总览

### 2.1 架构原则

> **同一套数据 + 同一 RAG 知识库 + 同一 LLM → 不同视角生成不同内容**

| 原则 | 说明 |
|-|-|
| 数据统一 | 加盟商轨道和总部轨道共用 Base 7 表 + dashboard_data.json，不建两套数据 |
| 知识统一 | RAG 知识库不分轨，检索时通过「视角过滤」决定返回哪些规则 |
| LLM 统一 | 同一模型（GLM-5.3-Flash ep-20260915164013-wjfvr），通过 Prompt 中的「角色设定」切换视角 |
| Skill 统一 | 同一套 function calling 工具集，不同视角暴露不同子集 |

### 2.2 加盟商轨道（自助视角）

**目标受众**：加盟商店主 / 门店长 / 店员  
**核心诉求**：我的店今天怎么样？钱有没有白花？接下来该做什么？

| 推送形态 | 触发时机 | 内容 | 频率上限 |
|-|-|-|-|
| **每日简报（A+）** | 每天 10:00 | 昨日销量/热销 TOP3/物料健康度/成本效率/今日行动建议 | 1 条/天 |
| **实时库存告警（C+）** | 每天 12:00/18:00 | 库存紧张物料 + 预计可用天数 + 一键补货入口 | 最多 2 条/天 |
| **周报复盘（B+）** | 每周一 9:00 | 上周汇总/环比/损耗率趋势/区域排名/下周建议 | 1 条/周 |
| **事件触发通知** | 配方变更/调拨待确认/盘点未完成/损耗率超标 | 单卡片单事件，含明确动作按钮 | 按需 |

**内容特征**：

- **颜色即结论**：🔴 马上行动 / 🟡 关注 / 🟢 正常
- **数字即成本**：所有库存问题翻译成「多少钱」
- **建议即行动**：不给诊断，给「下一步做什么」+ 一键操作入口
- **极简 newsletter**：单卡片 ≤ 5 个信息块，3 秒看完

**新增能力（相对于现有 ABC 系统）**：

- RAG 检索行业基准（如「本店损耗率 5.2% vs 行业均值 3%-5%」）
- LLM 生成个性化建议（基于历史采纳率优化推荐方向）
- 经营 Skill 一键调用（查库存/触发补货/提交盘点/确认调拨）

### 2.3 总部轨道（管理视角）

**目标受众**：总部运营 / 区域督导 / 采购负责人  
**核心诉求**：哪些门店有问题？什么问题？谁该负责？我该怎么干预？

| 推送形态 | 触发时机 | 内容 | 频率上限 |
|-|-|-|-|
| **加盟商诊断日报** | 每天 10:00 | 红灯门店列表/异常类型/根因判断/责任方/建议动作 | 1 条/天 |
| **加盟商对比周报** | 每周一 9:00 | 门店执行排名/盘点完成率/任务完成率/逾期率/损耗率排名 | 1 条/周 |
| **风险实时告警** | 异常检测触发 | 单门店单异常卡片，含下钻详情入口 | 按需 |
| **总部干预建议** | 每日/每周 | 需总部统一动作的聚合建议（如多门店同物料预警→供货延迟） | 1 条/天 |

**内容特征**：

- **红色即行动**：任何红色标记必须对应一条可执行动作
- **归因即派单**：根因判断 + 责任方 → 自动生成待办任务
- **下钻即详情**：任何汇总数字都能点进去看明细
- **对比即压力**：排名和均值让加盟商自然产生改进动力

**新增能力（相对于现有 Dashboard）**：

- RAG 检索历史归因案例（如「类似异常上次根因是什么、怎么解决的」）
- LLM 生成总部干预方案（如「3 家门店同时牛奶预警 → 建议总部紧急采购 200L」）
- 经营 Skill 批量操作（批量查询/批量派单/批量更新安全库存）

## 三、RAG 知识库架构设计

### 3.1 知识库内容分层

| 层级 | 内容 | 来源 | 更新频率 | 检索优先级 |
|-|-|-|-|-|
| **L0 指标字典** | 每个指标的名称/公式/口径/示例 | 系统定义 | 低频（随指标新增） | 最高（每次必查） |
| **L1 阈值速查表** | 各规则的红黄绿灯阈值 | 《库存异常判定 Knowhow》+ 行业数据 | 中频（季度校准） | 高（异常检测必查） |
| **L2 异常判定规则** | 11 条规则 + 5.5 现做茶饮专项 + 合并后 7 条 | 《库存异常判定 Knowhow》+ 审计文档 | 低频（规则变更时） | 高（触发时查） |
| **L3 行业基准** | 茶饮行业损耗率/周转天数/安全库存天数等 | CCFA/KwickOS/观远数据等 | 低频（年度更新） | 中（对比时查） |
| **L4 响应动作映射** | 每个异常 → 责任方 → 建议动作 → 系统动作 | 《门店间调拨 & 总部库存研判》 | 低频（流程变更时） | 中（生成建议时查） |
| **L5 加盟商专属档案** | 各门店历史异常/采纳率/偏好/特殊配置 | 系统运行积累 | 高频（每日更新） | 中（个性化时查） |
| **L6 历史案例库** | 已闭环的异常记录 + 归因结论 + 处理结果 | 建议反馈表 + 异常任务表 | 高频（每次闭环后） | 低（相似案例推荐时查） |

### 3.2 知识库物理结构

```
RAG 知识库（向量存储 + 结构化索引）
│
├── 📁 结构化索引（JSON/Key-Value，精确匹配）
│   ├── 指标字典.json          → 按指标名 O(1) 查
│   ├── 阈值速查表.json        → 按(物料类型, 规则名)查
│   ├── 加盟商档案.json        → 按(门店编码, 日期)查
│   └── 响应动作映射.json      → 按(异常类型, 责任方)查
│
├── 📁 向量存储（Embedding，语义检索）

│   └── 操作手册/SOP.md        → chunk 按流程拆分，检索操作指引

└── 📁 混合检索层
    ├── 查询分类器：判断查询类型（指标查询/规则查询/案例查询/建议生成）
    ├── 路由策略：结构化索引优先（精确）→ 向量存储兜底（语义）
```

### 3.4 可移植性设计

> **核心约束：知识库内容与 LLM 解耦，无论线上 LLM 还是本地模型都用同一套 RAG**

| 维度 | 阶段 1（线上 LLM） | 阶段 2（本地模型） | 移植成本 |
|-|-|-|-|
| **向量存储** | 内存/轻量向量库（如 faiss） | 本地向量数据库（如 Milvus/pgvector） | 低：导出 embedding 重建索引 |
| **Embedding 模型** | 线上 API（如 BGE/智谱） | 本地部署 Embedding 模型 | 中：需重新生成全部向量 |
| **知识库内容** | Markdown + JSON 文件 | 同一套文件 | **零成本**：内容完全不变 |
| **检索逻辑** | Python 脚本 | 同一套 Python 脚本 | 低：只需改 Embedding 调用端 |
| **Prompt 模板** | 线上调用 | 同一套模板 | **零成本**：模板完全不变 |
| **结构化索引** | JSON 文件 | 同一套 JSON 文件 | **零成本**：文件直接复制 |

**可移植性保障措施**：

1. **知识库内容纯文本化**：所有知识以 Markdown/JSON 存储，不绑定任何向量数据库特有格式
2. **Embedding 接口抽象化**：定义统一接口 `embed(text) -> vector`，底层可切换线上 API 或本地模型
3. **检索逻辑与生成逻辑分离**：检索层输出「上下文块」，生成层只消费上下文块，不感知检索细节
4. **版本管理**：知识库内容与代码分离，独立版本控制，支持回滚

## 四、经营 Skill 清单（Function Calling 工具集）

### 4.1 设计原则

- **同一套 Skill，不同视角暴露不同子集**：加盟商可见「自助操作」类 Skill，总部可见「批量管理」类 Skill
- **Skill 与 RAG 互补**：RAG 负责「知道什么」，Skill 负责「能做什么」
- **每个 Skill 有明确的输入/输出/副作用**：便于 LLM 决策何时调用

### 5.2 阶段 1 详细设计（线上 LLM + RAG MVP）

**5.2.1 RAG 检索链路**

```python
# 伪代码示意
def rag_retrieve(query, perspective="franchisee", store_code=None):
    # 1. 查询分类
    intent = classify_query(query)  # metric_lookup / rule_lookup / case_lookup / advice_gen

    # 2. 结构化索引检索（精确匹配）
    structured_results = []
    if intent == "metric_lookup":
        structured_results = search_metric_dict(query)
    elif intent == "rule_lookup":
        structured_results = search_threshold_table(query)

    # 3. 向量检索（语义匹配）
    query_embedding = embed(query)
    vector_results = vector_search(query_embedding, top_k=5)

    # 4. 加盟商档案过滤
    if store_code:
        store_profile = load_store_profile(store_code)
        # 将门店历史异常、采纳率注入上下文

    # 5. 结果融合
    fused = merge_results(structured_results, vector_results, store_profile)

    # 6. 按视角过滤
    if perspective == "franchisee":
        fused = filter_for_franchisee(fused)  # 过滤掉总部内部规则
    else:
        fused = filter_for_hq(fused)  # 过滤掉加盟商操作细节

    return format_context(fused)
```

```python
def generate_response(data_summary, rag_context, perspective, store_code):

数据摘要：
{data_summary}

相关规则与基准：
{rag_context}

请生成{perspective}视角的回复。
        """}
    ]

    response = call_glm(messages, endpoint="ep-20260915164013-wjfvr")

```

**5.2.3 Skill 调用链路**

```python
def handle_user_query(query, store_code, perspective):
    # 1. LLM 判断是否需要 Skill
    intent = llm_classify(query)

    if intent.requires_skill:
        skill_name, params = llm_extract_skill_params(query, intent)
        skill_result = execute_skill(skill_name, params)

        # 2. RAG 检索补充知识
        rag_context = rag_retrieve(query, perspective, store_code)

        # 3. LLM 生成最终回复
        return generate_response(skill_result, rag_context, perspective, store_code)
    else:
        # 纯知识问答，直接 RAG + LLM
        rag_context = rag_retrieve(query, perspective, store_code)
        return generate_response(None, rag_context, perspective, store_code)
```

**RAG 行业最佳实践（2026 共识）**

- **混合检索**（BM25 + 向量）是 production standard
- 企业级 RAG **不一定要上向量库**（与 GitHub Demo 的 R2 文本方案一致）
- 多模态是关键帧提取（美团"数智哨兵"提升视频巡检 5 倍）
- Chunking + 评估是生产 RAG 的核心难点

**关键数据点**：美团数智督导已服务 600+ 品牌 / 6 万+ 用户 / **降本 2 亿 / 创收 5 亿 / 差评率降 40%**；Crunchtime 150,000+ 门店；茶百道 8000+ 门店全部接入 LLM。

#### 5.5.2 我们方案的差异定位

**做对了的事（行业共识）**：

- ✅ **双轨推送**（加盟商 + 总部）= InfiSight / RestoSuite / 美团都有类似设计
- ✅ **RAG + LLM 解耦** = 行业最佳实践，知识库可移植
- ✅ **不调用 LLM 自动定责**，只用 D2/D1/S1/T2 硬规则 = 与 Crunchtime "AI 预测但人最终定责" 一致
- ✅ **Knowhow 沉淀为 R2 文本 + MVP 提炼版** = 验证"不上向量库也可行"
- ✅ **写入前确认机制** = RestoSuite "AI 助手问答但写操作需确认" 同源

**MVP 阶段不必补（成熟期再做）**：

- 硬件联动（摄像头 KDS）—— 美团路径，餐饮重资产
- 35 国多语言 / 多币种 / 强合规 —— RestoSuite 全球化模板
- 千店千面 / 强-弱管控切换 —— MVP 单品牌起步
- 业财一体化（财务模块）—— 金蝶路径，与库存 MVP 正交
- 摄像头 AI 巡检 —— 美团"数智哨兵"，硬件投入大

**MVP 该补的颗粒度**：

- **强/弱管控边界**明确写进架构（什么数据总部可见、什么加盟商私有）—— RestoSuite 的核心命题
- **多门店切换**（"我的店" vs "总部看所有店"）—— 前端要补，Base 已经能切
- **异常预警指标系统化**（11 条 → 28-50 条覆盖：客单价 / 损耗率 / 复购 / 缺货等）—— 美团 98 个指标可参照，按 MVP 节奏加
- **派单工单完整链路**（派发 → 执行 → 凭证 → 关闭）—— InfiSight / 美团都有

#### 5.5.3 一句话定位

<callout emoji="🎯">
架构思路是**行业共识的精简 MVP 版**。国内 RestoSuite / 美团 / InfiSight 三家加起来覆盖的能力就是我们的远景——MVP 只取"**AI 助手问答 + 预警 + 闭环派单**"三块；硬件联动、全球化、业财一体放到后续迭代。
</callout>

## 附录 D：异常判定决策树（rules/d2_d1_s1_t2.json）

4 类硬规则的判定流程。前端代码 100% 执行，**不调用 LLM**。输出统一为 5 档：有证据 / 已排除 / 疑似 / 证据不足 / 待盘点。

### D.1 统一输出档位定义

| 档位 | code | 含义 | 处理建议 |
|-|-|-|-|
| 有证据 | `confirmed` | 硬规则命中 + 证据齐全 | 直接派单 + 闭环 |
| 已排除 | `excluded` | 硬规则不命中 | 归档 |
| 疑似 | `suspect` | 规则命中 + 证据部分缺失 | LLM 归因 + 人工 review |
| 证据不足 | `insufficient` | 关键证据缺失（无入库/无销售/无盘点） | 门店补凭证后再判定 |
| 待盘点 | `pending_count` | 无最近盘点基线 | 强制盘点任务 |

### D.2 D2 负库存决策树

| 条件 | 判定 | 档位 | severity |
|-|-|-|-|
| 期末库存 < 0 | 负库存确认 | `confirmed` | critical |
| 期末库存 < 0 + 已标记异常消耗 | 已知异常，确认 | `confirmed` | critical |
| 期末库存 ≥ 0 | 正常 | `excluded` | - |
| 期末库存 ≥ 0 + 销售明细缺失 ≥ 2 天 | 疑似漏记销售 | `suspect` | warning |
| 缺入库记录 ≥ 3 天 + 期末 ≥ 0 | 无法判定 | `insufficient` | warning |
| 缺期初库存 | 需盘点建基线 | `pending_count` | warning |

### D.3 D1 理论与实盘差异决策树

| 条件 | 判定 | 档位 | severity |
|-|-|-|-|
| 差异率 < -5%（按物料阈值） | 盘亏确认 | `confirmed` | critical |
| 差异率 > +5% | 盘盈确认 | `confirmed` | info |
| 差异率 ±5% 内 | 正常 | `excluded` | - |
| 缺最近盘点（> 7 天） | 无法判定 | `pending_count` | warning |
| 差异率在阈值边界 ±1% | 疑似 | `suspect` | warning |
| 理论值计算缺字段 | 数据缺失 | `insufficient` | warning |

### D.4 S1 安全库存决策树

| 条件 | 判定 | 档位 | severity |
|-|-|-|-|
| 期末 < 安全 × 物料阈值 | 预警确认 | `confirmed` | warning |
| 期末 ≥ 安全 × 1.5 | 正常 | `excluded` | - |
| 安全库存 = 0（未配置） | 配置缺失 | `insufficient` | info |
| 安全库存 > 90 天消耗 | 配置过大 | `excluded` | info |
| 期末 ∈ [安全 × 阈值, 安全 × 1.5） | 接近安全 | `suspect` | info |

### D.5 T2 销入比决策树

| 条件 | 判定 | 档位 | severity |
|-|-|-|-|
| 销入比 > 上限（按物料阈值） | 异常消耗确认 | `confirmed` | warning |
| 销入比 < 下限（按物料阈值） | 漏记销售确认 | `confirmed` | critical |
| 销入比 ∈ [下限, 上限] | 正常 | `excluded` | - |
| 无入库记录 | 数据缺失 | `insufficient` | warning |
| 销入比超出阈值 + 促销期标记 | 疑似促销误报 | `suspect` | info |
| 时间窗口 < 7 天 | 样本不足 | `insufficient` | info |

<callout emoji="🔧">
**Codex 实现提示**：决策树建议用 JSON Schema 描述，前端用 `json-rules-engine` 或自写 if-else 链执行。5 档输出后传给响应动作映射（附录 E）查表。
</callout>

### E.3 闭环机制

1. **派单**：诊断日报生成后，按映射表查 owner_role，自动 @ 加盟商私聊 + 总部群
2. **执行**：门店按 owner_action 操作，上传凭证（图片/PDF）
3. **复核**：系统重跑 D2/D1/S1/T2 判定，若 `confirmed` 转 `excluded` 即关闭
4. **升级**：SLA 超时 → escalation_role 接单；连续 2 次未关闭 → 区域经理
5. **归档**：异常案例写入历史案例库，作为后续 RAG 检索的种子

<callout emoji="🔄">
**反馈闭环**：加盟商可在 IM 卡片点 "误报" / "已处理" / "申请重判"，对应动作回写 response_action_map 的 `feedback_count`，作为下次阈值校准的依据。
</callout>

### H.1 加盟商视角 5 个场景

#### 场景 1 · 今日销量诊断

**触发 query**："我今天的销量怎么样？"

**期望响应（≤ 60s）**：今日销量 + 昨日同比 + 7 日均量 + 归因（天气/竞品/物料）+ 建议操作（生成促销方案/补货/忽略）

**验收标准**：响应 ≤ 60s · 3 个数据点 · ≥2 个归因 · ≥1 个可执行按钮 · 数据来源标注

#### 场景 2 · 物料损耗归因

**触发 query**："为什么我的半成品奶茶损耗比平时高？"

**期望响应（≤ 60s）**：7 日损耗率对比 + 6 类根因分类（数据/单据/物理/偷盗/顾客/系统）+ 概率分布 + 督导派单动作

**验收标准**：响应 ≤ 60s · 6 类根因覆盖 · 概率合理 · ≥1 个动作按钮

#### 场景 3 · 智能补货建议

**触发 query**："我现在需要补什么货？"

**期望响应（≤ 60s）**：按 4 级严重程度（critical / warning / info）+ 剩余量/阈值/可支撑天数 + 自动生成调拨单/采购单

**验收标准**：响应 ≤ 60s · 4 级分级 · 含具体数字 · ≥1 个可执行动作 · 不催促语气

#### 场景 4 · 异常确认与执行（D2 负库存）

**触发 query**："我看到了一个 D2 负库存异常，要怎么处理？"

**期望响应（≤ 60s）**：异常数据回显 + 历史上下文（入库/销售/调拨）+ ≥3 个可能原因 + 每个原因有动作（查看/补录/派单）

**验收标准**：响应 ≤ 60s · 异常数据完整 · ≥3 个原因 · 每个原因有动作 · 不直接定责到人

#### 场景 5 · 周报推送

**触发 query**："我上周门店整体怎么样？"

**期望响应（≤ 60s）**：4 核心指标（销量/毛利率/异常/周期）+ 异常按档位分类（疑似/已排除）+ 下周关注清单

**验收标准**：响应 ≤ 60s · 4 个核心指标 · 异常按档位分类 · ≥1 个动作按钮 · 周期明确

### H.2 总部视角 5 个场景（含 1 分钟归因经典）

#### **场景 6 ⭐ · 区域利润下滑归因（1 分钟归因经典场景）**

**触发 query**："上周华东区利润下滑了 12%，原因是什么？"

**期望响应（≤ 60s，含 LLM 调用）**：利润归因树 5 层拆解

**1. 收入下滑**（贡献 -65%）：销量 -7.6% + 客单价 -3.4%

**2. 成本上升**（贡献 +25%）：物料成本 +12.2%（半成品损耗 / 报损异常）+ 人工 +8.2%

**3. 异常损耗**（贡献 +15%）：5 家门店 12 次异常 + Top 3 门店 + Top 3 物料

**4. 价格策略**（贡献 -10%）：9/10 平台促销 -8% 持续 7 天

**5. 季节性因素**（贡献 -25%）：9 月上旬华东连续阴雨 -8% 客流

**建议行动（按 ROI 排序）**：① 半成品奶茶损耗核查（预计挽回 ¥8,000/周）② 黑糖珍珠报损专项（¥4,500/周）③ 促销策略复盘（¥6,000/周）④ 季节性营销（¥3,500/周）

**动作按钮**：[派单 Top 3 门店] [生成区域诊断报告] [深度归因]

**验收标准（⭐MVP 验收核心场景⭐）**：响应 ≤ 60s · 归因树 ≥ 3 层 · 5 类原因覆盖 · 每个原因有数据 · 建议按 ROI 排序 · ≥3 个可执行动作按钮

#### 场景 7 · 高风险加盟商识别

**触发 query**："哪个加盟商需要重点关注？"

**期望响应（≤ 60s）**：Top 5 高风险加盟商 + 健康度评分（52-67 区间）+ 具体异常 + 建议（派单/补货/培训）+ 总体健康度分布

**验收标准**：响应 ≤ 60s · Top 5 排序 · 每个加盟商含异常+建议 · 总体分布 · ≥3 个动作按钮

#### 场景 8 · 新品上线表现分析

**触发 query**："新品 Black Sugar Boba Milk Tea 上线 2 周了，表现怎么样？"

**期望响应（≤ 60s）**：14 天销售数据 + 4 个维度（整体/杯型/糖量/门店）+ Top 5 门店 + 与对照 SKU 对比 + 异常识别（STORE015 / 未上线门店）

**验收标准**：响应 ≤ 60s · 周期明确 · 4 个数据维度 · Top 5 排序 + 异常识别 · ≥3 个建议动作

#### 场景 9 · 异常根因分布（6 类）

**触发 query**："这周的异常主要是什么类型？"

**期望响应（≤ 60s）**：异常总数 + 6 类根因分布（数据录入 36% / 单据流转 25% / 物理损耗 20% / 偷盗 9% / 顾客 6% / 系统 5%）+ Top 物料 + Top 表现 + 关键洞察

**验收标准**：响应 ≤ 60s · 6 类根因全覆盖 · 占比合理 · Top 物料具体 · ≥3 个动作按钮

#### 场景 10 · 预测性预警

**触发 query**："下个月我们应该重点关注什么？"

**期望响应（≤ 60s）**：下月预测周期 + 3 个预测维度（销量预测 / 风险预警 / 优化机会）+ ≥5 个时序建议动作（本周/下周/10 月初/中/末）
