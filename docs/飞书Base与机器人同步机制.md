# 飞书 Base 与机器人同步机制

> 状态：当前项目事实基线  
> 最后核对：2026-09-20  
> 目的：供 Codex、豆包工作和项目维护者恢复上下文；不得把飞书数据同步误解为 Excel/附件导入。

页面与完整功能入口请同时参阅 [现有功能盘点与改造索引.md](现有功能盘点与改造索引.md)；后台已有专用“飞书同步”页面 `/sync/`。

## 1. 一句话结论

本项目已经复用同一套飞书自建应用/机器人能力：

- `FEISHU_APP_ID` + `FEISHU_APP_SECRET` 用于取得 tenant access token，并以只读方式读取飞书 Base、项目文档和云盘交付物；
- `FEISHU_WEBHOOK_URL` + `FEISHU_SIGNING_SECRET` 用于机器人主动推送群消息；
- `FEISHU_VERIFICATION_TOKEN` 用于校验飞书事件回调；
- Cloudflare Worker 每 10 分钟执行定时任务，把有效数据规范化后保存到 R2，再供库存台账、研判、工单和提醒使用。

飞书是上游数据源和消息渠道，不是第二套业务状态系统；工单状态、人工处理记录、盘点、收货和调拨等 Demo 业务状态保存在系统 R2 中。

## 2. 当前真实运行链路

```text
飞书 Base
  ├─ 门店销售明细
  ├─ 商品 BOM
  └─ 物料主数据
       ↓ 飞书 OpenAPI（应用身份，只读）
Cloudflare Worker 定时任务（每 10 分钟）
       ↓ 字段校验、SKU 映射、BOM 完整性门禁
R2 快照 / Demo 业务状态
       ↓
销售汇总 → BOM 消耗拆解 → 理论库存 → 规则研判 → 工单/提醒
       ↓
飞书机器人 Webhook（按配置推送，不承载业务主状态）
```

对应实现：

- 定时器：`wrangler.jsonc` 的 `*/10 * * * *`；
- 获取应用 token：`getFeishuTenantToken()`；
- Base 分页读取：`listFeishuRecords()`，每页最多 500 条，并对 `Data not ready` 做 3 次退避重试；
- R2 主同步：`r2ImportFeishuSales()`；
- 手工同步：总部在 `/sync/` 创建异步任务，调用 `POST /api/feishu-sync/jobs`，再通过 `GET /api/feishu-sync/jobs/latest` 或任务 ID 查询排队、运行、完成和失败状态；页面离开后任务仍可继续；
- 兼容刷新：`POST /api/feishu-sync/refresh` 仍保留给内部维护；加 `?force=1` 可绕过 90 秒冷却，但会同步更新线上 R2 快照；
- 同步查询：`GET /api/feishu-sync/state`；
- 机器人发送：`notifyFeishu()` / 通知配置页面；
- 项目文档与云盘交付物：定时调用 `syncFeishuProjectDocument()`、`syncFeishuProjectFiles()` 保存只读知识快照。

## 3. 当前同步的数据口径

当前 R2 库存主链路实时读取 3 张表：

| 数据 | Base table_id | 当前用途 |
|---|---|---|
| 门店销售明细 | `tbly9ewKpWTpeQzC` | 按门店、营业日、SKU 汇总销售 |
| 商品 BOM | `tbl3DtZPX3kwct1A` | 将商品销量拆解为物料理论消耗 |
| 物料主数据 | `tblFTA3dL0z2gNFu` | 解析 BOM 关联物料、单位与名称 |

项目还配置了商品档案、库存台账、调拨主表、调拨明细和门店库存流水等表 ID，但当前 R2 正式演示链路没有把它们全部作为实时库存事件入账。收货、报损和调拨目前以系统事件为准，不能写成“9 张 Base 表都在实时同步”。

## 4. 销售记录被接受的必要条件

一条 Base 销售记录只有同时满足下列条件，才进入本次同步快照：

1. 有飞书 `record_id`；
2. `门店编码关联` 可以解析成非空门店编码；
3. `日期` 可以解析为 `YYYY-MM-DD` 营业日；
4. `销售数量` 是大于或等于 0 的数值；
5. SKU 优先读取 `SKU Code`，否则使用 `商品` 或 `商品名称(OCR)` 做本地别名映射。

`销售金额`用于汇总，但不是记录进入同步的硬门禁。没有有效 BOM 的 SKU 可以进入销售汇总，但不得参与物料库存扣减，并会进入“待治理 SKU”。

因此“今天在飞书上传了数据”不等于“系统已经识别为今天的营业日”。应先在同步页核对：

- 最近同步时间；
- 最新有效营业日；
- 扫描数与有效导入数；
- 已映射/未映射销售记录；
- BOM 完整性与待治理 SKU。

## 5. BOM 与库存安全边界

- 飞书 Base 保持只读，系统不会回写原始销售或 BOM；
- Brown Sugar 品牌 BOM 必须通过完整性门禁，未通过时回退到已验证快照；
- 无 BOM 的销售不扣物料，避免错误回算；
- 销售、BOM 和主数据形成版本化导入快照；工单必须引用研判快照，而不是直接引用不断变化的 Base 当前值；
- 收货确认、调拨签收、盘点完成后，由系统事件触发规则重算并保留前后结果；
- `force=1` 会更新线上 R2 快照，演示前必须先做只读检查，不能把强制刷新当成普通查询。

## 6. 机器人与 Base 的职责区别

| 能力 | 身份/接口 | 职责 |
|---|---|---|
| 读取 Base/文档/云盘 | 飞书自建应用 + tenant access token | 获取只读业务数据与协作文档 |
| 主动发消息 | 群机器人 Webhook | 投递异常提醒、日报和预览卡片 |
| 接收事件 | 飞书事件回调 + verification token | 接收消息/卡片动作（按已开放路由） |
| 业务状态 | Worker + R2 | 保存工单、处理记录、盘点、收货、调拨和闭环状态 |

口头上可以统称“飞书机器人已经接入”，但排查时必须区分“应用读 Base”和“机器人发消息”两条链路。

## 7. 每次恢复项目时的检查顺序

1. 先读本文件和 `references/progress-doc.md`；
2. 检查 `wrangler.jsonc` 的 cron 和 R2/D1 binding；
3. 检查 `src/worker.js` 中的 Base token、table ID 和 `r2ImportFeishuSales()`；
4. 只读调用同步状态，确认最新有效营业日和数据质量；
5. 若飞书已上传但营业日未更新，先检查 Base 字段名、字段类型和记录值，不要直接造数据；
6. 只有需要更新线上快照时才发起手工同步；优先使用 `/sync/` 的异步任务并查看最终状态，不要重复点击；需要重建门店营业日的 Demo 编排属于有状态操作，必须另行确认。

## 8. 目前仍需补齐

- 为 Base 同步增加逐原因拒绝计数，例如缺门店、缺日期、数量无法解析、SKU 无法映射；
- 在同步页明确区分“飞书已扫描”“有效导入”“参与库存回算”三层数量；
- 将正式收货、报损、调拨事件表接入前，先锁定字段、状态机、幂等键和营业日口径；
- 正式实现事件回调时，补签名校验、重放保护、幂等处理和失败审计；
- 机器人卡片只负责触达和跳转，关闭工单仍由系统权限与门禁控制。
