# 人员组织与工单流转 MVP 设计 v1

> 目标：补齐 Demo 当前缺失的账号、组织、责任分配和工单移交能力，使门店、区域督导和总部可以围绕同一张工单完成闭环。

## 1. MVP 模拟组织

```text
MOMOYO 品牌总部
├─ 品牌运营中心
│  └─ 王敏｜总部库存运营
└─ 雅加达北区
   ├─ Rina｜区域督导
   └─ STORE001
      ├─ 陈店长｜门店负责人
      └─ 小李｜店员
```

原型中的三个演示账号：

| 账号 | 角色 | 组织范围 | 默认工作台 |
|---|---|---|---|
| 小李 | 门店店员 | STORE001 | 门店任务、日常运营、门店助手 |
| Rina | 区域督导 | 雅加达北区及所属 7 店 | 区域经营、巡店、派发与升级 |
| 王敏 | 总部库存运营 | 全部区域 | 风险监测、跨区治理与总部工单 |

正式系统可先用邮箱/OAuth 登录；总部账号后续可同步飞书通讯录。演示账号只用于验证权限和流转，不代表最终认证方案。

## 2. 最小数据对象

### User 用户

- `user_id`
- `display_name`
- `login_identity`
- `status`

### OrgUnit 组织单元

- `org_id`
- `org_type`: `brand / department / region / store`
- `parent_org_id`
- `name`

### UserOrgRole 任职关系

- `user_id`
- `org_id`
- `role_code`: `store_staff / store_manager / supervisor / hq_operator`
- `is_primary`
- `valid_from / valid_to`

一个人可拥有多个任职关系，但每次访问必须明确当前身份和可见范围。

### WorkOrderAssignment 工单责任

- `work_order_id`
- `owner_org_id`: 当前承担结果责任的组织
- `owner_role`: 当前应处理角色
- `assignee_user_id`: 当前具体负责人，可为空
- `assigned_at`
- `due_at`
- `assignment_status`

### WorkOrderHandoff 工单移交

- `handoff_id`
- `work_order_id`
- `from_org_id / from_user_id`
- `to_org_id / to_role / to_user_id`
- `reason_code`
- `note`
- `created_at`

必须区分四个概念：

- 责任组织：谁对结果负责；
- 当前负责人：现在由谁推进；
- 操作人：谁执行了某次动作；
- 创建人：谁或哪个系统创建工单。

## 3. 工单流转原则

1. 一项异常只保留一张主工单，不因升级复制工单。
2. 门店能够完成的业务事实核对，默认分配给门店组织。
3. 店员可以处理；需要负责人权限的动作由店长确认。
4. 门店求助、超时或多次重算未恢复时，转交所属区域督导。
5. 跨店共性、供应、规则、BOM、单位和主数据问题升级总部责任组。
6. 升级后原门店仍可补充证据，但不再承担总部治理动作。
7. 总部修复后触发关联工单重算；恢复不等于自动关闭，仍需当前责任人填写闭环结论。
8. 每次分配、接受、转交、退回和关闭都写入不可覆盖的时间线。

## 4. 示例：黑糖珍珠负库存

```text
09:05 规则 V2 触发 D2
      owner_org=STORE001，owner_role=store_staff
09:12 小李查看并开始核对
10:05 小李发现调拨签收无法确认，点击“需要帮助”
      工单转交雅加达北区，assignee=Rina
10:20 Rina 远程核查，发现多店存在相同单位偏差
      升级总部商品与主数据组，assignee=王敏
11:30 王敏修正单位版本，系统批量重算关联工单
11:31 D2 恢复，王敏填写治理结论
11:40 门店陈店长确认实际库存，工单关闭
```

工单页面必须始终展示：来源、当前责任组织、负责人、截止时间、最近一次转交原因和完整流转时间线。

## 5. 权限边界

| 动作 | 店员 | 店长 | 区域督导 | 总部运营 |
|---|---:|---:|---:|---:|
| 查看本店任务 | 是 | 是 | 所辖门店 | 按授权范围 |
| 补充证据/处理记录 | 是 | 是 | 是 | 是 |
| 提交普通业务草稿 | 是 | 是 | 可协助 | 可协助 |
| 确认高风险写入 | 否 | 是 | 按授权 | 按授权 |
| 请求督导帮助 | 是 | 是 | — | — |
| 派发巡店任务 | 否 | 否 | 是 | 可派发总部专项 |
| 升级总部治理 | 否 | 可建议 | 是 | — |
| 修改品牌规则/主数据 | 否 | 否 | 否 | 是 |
| 关闭工单 | 按工单类型 | 是 | 当前责任范围 | 当前责任范围 |

所有库存、收货、调拨、盘点、报损等正式写入继续保留人工确认。

## 6. 页面改造

### 门店端

- 顶部显示当前账号、门店及上级责任人；
- 每张任务卡显示责任组织和执行人；
- “需要帮助”触发责任移交，而不是另建提醒；
- 门店助手自动带入当前账号权限，不允许越权执行。

### 督导端

- 显示所辖区域和门店范围；
- 分开“门店仍负责”和“已转交给我”；
- 支持接受、重新指派、创建巡店任务和升级总部；
- 区域指标只能下钻到有权限的门店。

督导在移动端点击提醒后先看到责任移交摘要，随后有两条路径：

1. “查看原工单”：进入同一张工单的移动详情页，查看处理目标、研判证据、当前责任人和完整时间线；
2. “接受并记录介入”：写入一条 assignment/handoff 事件，将具体负责人更新为督导本人，然后进入工单详情继续处理。

接受后才开放“记录联系门店、核对调拨签收、派发现场复核、升级总部”等动作。每个动作追加到原工单时间线，不另建一张督导工单。移动详情页底部保留当前主动作，避免督导返回列表后失去上下文。

### 总部端

- 显示当前总部岗位和品牌范围；
- 聚合问题保留所有来源工单，不覆盖门店处理历史；
- 可将问题分派给商品、供应链、财务或数据治理等责任组；
- 治理动作完成后，对关联工单批量重算并分别闭环。

## 7. 实现顺序

截至 2026-09-18，第 1 步的 Demo 配置能力已完成：后台可维护演示账号、角色与组织范围，并可切换当前身份。数据暂存 R2，尚未升级为正式登录和 API 权限门禁。

1. 建立 `users / org_units / user_org_roles` 三个基础表和演示数据；
2. 给工单增加责任组织、责任角色、负责人和截止时间；
3. 新增 assignment 与 handoff 时间线事件；
4. 接入登录后的身份与数据范围过滤；
5. 改造门店求助、督导接受、升级总部和退回动作；
6. 给所有单据写入补充 `created_by / operated_by / confirmed_by`；
7. 用 D2 主链验证“门店 → 督导 → 总部 → 重算 → 关闭”；
8. 最后接入飞书通讯录同步与正式 OAuth。

## 8. MVP 验收标准

- 任一工单都能回答“现在谁负责、为什么转给他、下一步由谁做”；
- 三个演示账号只能看到各自授权范围；
- 转交后不生成重复工单；
- 操作记录保留真实操作人，系统动作标记为系统规则引擎；
- 人员离职或调岗后，历史记录不丢失，未完成工单可重新分配；
- 从门店触发到总部关闭的完整时间线可以回放。

## 9. 当前后台数据模拟（2026-09-18）

移动端原型采用当前线上 `/api/state` 中仍开放的 `OPT-0868AD91` 作为督导介入样例，不再使用已经闭环的黑糖珍珠 D2 工单。

- 门店：`STORE001`
- 物料：茶叶（kg）
- 规则：`S1_SAFETY_STOCK`
- 当前状态：`pending_store_submission`
- 原责任人：`STORE001 店长`
- 理论库存 / 实盘库存：`1.74 / 1.74 kg`
- 安全库存：`2 kg`，确认缺口 `0.26 kg`
- 数据缺口：历史营业日没有找到相关订货与在途单据
- 规则建议：查看订货与在途、建立紧急补货草稿、查看调拨单、查看库存流水

原型模拟路径为：督导查看原工单 → 接受介入并写入责任事件 → 建立关联原工单的紧急补货草稿 → 等待门店核对采购包装与数量后提交。该原型只模拟交互，不修改线上业务数据；正式接入时复用现有订货草稿和工单时间线接口。

门店端同时补齐两条可操作链路：

1. “开始核对”进入同一张 `OPT-0868AD91` 的移动工单页；门店可以查看规则证据和后台原工单，记录开始处理，建立关联补货草稿，查看邻店调拨，或把同一工单移交督导。
2. “去确认”进入收货详情；人工填写实收数量和差异原因后，系统按照“收货单确认 → 库存流水 → V2 自动重算 → 工单等待人工闭环”的顺序更新后台。

当前线上快照没有待收货单，因此收货详情采用 `PO-SIM-S1-001 / RCV-SIM-S1-001` 模拟后续业务状态，页面明确保持为原型，不向线上接口写入。正式落地时应读取 `purchaseOrders / receiptOrders`，只有真实状态为 `pending_receipt / draft` 的单据才生成门店提醒；确认动作调用现有收货确认接口，并把返回的事件编号、最新 V2 快照和工单状态重新渲染到移动页。

## 10. 门店端与总部后台统一原则

门店移动端、督导端和总部后台不是三套任务系统，而是同一 `operation_task` 的不同权限视图：

- 共用工单编号、规则来源、责任组织、负责人和状态；
- 门店“开始处理”、建立补货草稿和确认收货，均追加到同一时间线；
- 订货单、收货单和库存流水通过 `source_work_order_id` 关联原工单；
- 收货确认后自动生成库存流水和最新 V2 快照，总部后台立即看到库存修正前后变化；
- 总部关闭工单时必须通过统一门禁：业务凭证存在、最新 V2 已恢复、最终原因和解决方式已填写、门店已采纳、总部已确认；
- 页面差异只来自角色权限与信息密度，不允许出现互相矛盾的状态或复制工单。

原型中的总部“跟进工单”已按照正式后台的全页详情结构绘制，包括工单与责任、研判过程、建议动作、关联单据、库存修正、完整时间线、后台业务入口和人工闭环门禁。门店端模拟操作会同步改变后台原型中的单据状态、理论库存、V2 状态与时间线，用于验证统一模型。
