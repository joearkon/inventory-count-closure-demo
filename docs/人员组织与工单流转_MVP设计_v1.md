# 人员组织与工单流转 MVP 设计 v1

> 目标：补齐 Demo 当前缺失的账号、组织、责任分配和工单移交能力，使门店、区域督导和总部可以围绕同一张工单完成闭环。

## 1. MVP 模拟组织

```text
MOMOYO 品牌总部
├─ 品牌运营中心
│  └─ 王敏｜总部库存运营
└─ 雅加达北区
   ├─ Rina｜区域督导
   └─ STORE001
      ├─ 陈店长｜门店负责人
      └─ 小李｜店员
```

原型中的三个演示账号：

| 账号 | 角色 | 组织范围 | 默认工作台 |
|---|---|---|---|
| 小李 | 门店店员 | STORE001 | 门店任务、日常运营、门店助手 |
| Rina | 区域督导 | 雅加达北区及所属 7 店 | 区域经营、巡店、派发与升级 |
| 王敏 | 总部库存运营 | 全部区域 | 风险监测、跨区治理与总部工单 |

正式系统可先用邮箱/OAuth 登录；总部账号后续可同步飞书通讯录。演示账号只用于验证权限和流转，不代表最终认证方案。

## 2. 最小数据对象

### User 用户

- `user_id`
- `display_name`
- `login_identity`
- `status`

### OrgUnit 组织单元

- `org_id`
- `org_type`: `brand / department / region / store`
- `parent_org_id`
- `name`

### UserOrgRole 任职关系

- `user_id`
- `org_id`
- `role_code`: `store_staff / store_manager / supervisor / hq_operator`
- `is_primary`
- `valid_from / valid_to`

一个人可拥有多个任职关系，但每次访问必须明确当前身份和可见范围。

### WorkOrderAssignment 工单责任

- `work_order_id`
- `owner_org_id`: 当前承担结果责任的组织
- `owner_role`: 当前应处理角色
- `assignee_user_id`: 当前具体负责人，可为空
- `assigned_at`
- `due_at`
- `assignment_status`

### WorkOrderHandoff 工单移交

- `handoff_id`
- `work_order_id`
- `from_org_id / from_user_id`
- `to_org_id / to_role / to_user_id`
- `reason_code`
- `note`
- `created_at`

必须区分四个概念：

- 责任组织：谁对结果负责；
- 当前负责人：现在由谁推进；
- 操作人：谁执行了某次动作；
- 创建人：谁或哪个系统创建工单。

## 3. 工单流转原则

1. 一项异常只保留一张主工单，不因升级复制工单。
2. 门店能够完成的业务事实核对，默认分配给门店组织。
3. 店员可以处理；需要负责人权限的动作由店长确认。
4. 门店求助、超时或多次重算未恢复时，转交所属区域督导。
5. 跨店共性、供应、规则、BOM、单位和主数据问题升级总部责任组。
6. 升级后原门店仍可补充证据，但不再承担总部治理动作。
7. 总部修复后触发关联工单重算；恢复不等于自动关闭，仍需当前责任人填写闭环结论。
8. 每次分配、接受、转交、退回和关闭都写入不可覆盖的时间线。

## 4. 示例：黑糖珍珠负库存

```text
09:05 规则 V2 触发 D2
      owner_org=STORE001，owner_role=store_staff
09:12 小李查看并开始核对
10:05 小李发现调拨签收无法确认，点击“需要帮助”
      工单转交雅加达北区，assignee=Rina
10:20 Rina 远程核查，发现多店存在相同单位偏差
      升级总部商品与主数据组，assignee=王敏
11:30 王敏修正单位版本，系统批量重算关联工单
11:31 D2 恢复，王敏填写治理结论
11:40 门店陈店长确认实际库存，工单关闭
```

工单页面必须始终展示：来源、当前责任组织、负责人、截止时间、最近一次转交原因和完整流转时间线。

## 5. 权限边界

| 动作 | 店员 | 店长 | 区域督导 | 总部运营 |
|---|---:|---:|---:|---:|
| 查看本店任务 | 是 | 是 | 所辖门店 | 按授权范围 |
| 补充证据/处理记录 | 是 | 是 | 是 | 是 |
| 提交普通业务草稿 | 是 | 是 | 可协助 | 可协助 |
| 确认高风险写入 | 否 | 是 | 按授权 | 按授权 |
| 请求督导帮助 | 是 | 是 | — | — |
| 派发巡店任务 | 否 | 否 | 是 | 可派发总部专项 |
| 升级总部治理 | 否 | 可建议 | 是 | — |
| 修改品牌规则/主数据 | 否 | 否 | 否 | 是 |
| 关闭工单 | 按工单类型 | 是 | 当前责任范围 | 当前责任范围 |

所有库存、收货、调拨、盘点、报损等正式写入继续保留人工确认。

## 6. 页面改造

### 门店端

- 顶部显示当前账号、门店及上级责任人；
- 每张任务卡显示责任组织和执行人；
- “需要帮助”触发责任移交，而不是另建提醒；
- 门店助手自动带入当前账号权限，不允许越权执行。

### 督导端

- 显示所辖区域和门店范围；
- 分开“门店仍负责”和“已转交给我”；
- 支持接受、重新指派、创建巡店任务和升级总部；
- 区域指标只能下钻到有权限的门店。

督导在移动端点击提醒后先看到责任移交摘要，随后有两条路径：

1. “查看原工单”：进入同一张工单的移动详情页，查看处理目标、研判证据、当前责任人和完整时间线；
2. “接受并记录介入”：写入一条 assignment/handoff 事件，将具体负责人更新为督导本人，然后进入工单详情继续处理。

接受后才开放“记录联系门店、核对调拨签收、派发现场复核、升级总部”等动作。每个动作追加到原工单时间线，不另建一张督导工单。移动详情页底部保留当前主动作，避免督导返回列表后失去上下文。

### 总部端

- 显示当前总部岗位和品牌范围；
- 聚合问题保留所有来源工单，不覆盖门店处理历史；
- 可将问题分派给商品、供应链、财务或数据治理等责任组；
- 治理动作完成后，对关联工单批量重算并分别闭环。

## 7. 实现顺序

1. 建立 `users / org_units / user_org_roles` 三个基础表和演示数据；
2. 给工单增加责任组织、责任角色、负责人和截止时间；
3. 新增 assignment 与 handoff 时间线事件；
4. 接入登录后的身份与数据范围过滤；
5. 改造门店求助、督导接受、升级总部和退回动作；
6. 给所有单据写入补充 `created_by / operated_by / confirmed_by`；
7. 用 D2 主链验证“门店 → 督导 → 总部 → 重算 → 关闭”；
8. 最后接入飞书通讯录同步与正式 OAuth。

## 8. MVP 验收标准

- 任一工单都能回答“现在谁负责、为什么转给他、下一步由谁做”；
- 三个演示账号只能看到各自授权范围；
- 转交后不生成重复工单；
- 操作记录保留真实操作人，系统动作标记为系统规则引擎；
- 人员离职或调岗后，历史记录不丢失，未完成工单可重新分配；
- 从门店触发到总部关闭的完整时间线可以回放。
