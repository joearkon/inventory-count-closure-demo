# 库存研判闭环设计 v1

## 目标

闭环不是“上传凭证后关闭工单”，而是保留发现、判断、执行、验证和人工结论的完整链路。规则负责重算事实，人负责解释最终原因和承担业务决策。

## 最小闭环

```text
发现异常
→ 冻结首次 V2 研判快照
→ 建立跟进工单
→ 执行并关联盘点/调拨/订货/收货/报损单据
→ 重新运行 V2
→ 比较处理前后结果
→ 人工选择闭环结果
→ 已恢复 / 接受例外 / 误判 / 转治理 / 继续处理
```

## 工单必须保存的内容

### 首次快照

- 来源研判编号、门店、营业日、物料和单位；
- V1 规则、V2 规则及版本；
- 库存重建值、实盘值和证据引用；
- 首要排查位置、第一假设、缺失证据；
- 决策轨迹和建议动作 ID。

### 执行记录

- 人工处理记录；
- 关联盘点单、调拨单、订货单、收货单、报损单和库存流水；
- 每次操作人、时间、动作前后状态；
- 单据只关联，不覆盖首次研判快照。

### 验证快照

- 业务动作完成后手动或自动重新运行 V2；
- 每次运行生成新的 `diagnosis_run_id`；
- 保存新事实、规则版本、异常状态和缺失证据；
- 页面并排展示首次与最新结果，禁止覆盖历史。

## 人工闭环结果

| 结果 | 使用条件 | 后续动作 |
|---|---|---|
| 已恢复 | 最新 V2 不再触发，且关键单据已关联 | 正常关闭 |
| 接受例外 | 仍触发，但属于经授权的正常业务情况 | 填写理由、批准人和有效期，超期复查 |
| 规则误判 | 事实正确但规则不适用 | 关闭工单，进入规则改进清单 |
| 主数据问题 | BOM、单位、价格、安全库存或映射错误 | 转总部治理工单，原工单等待治理后复算 |
| 尚未解决 | 仍触发且不能合理解释 | 不允许关闭，继续执行或升级 |

## 关闭门禁

MVP 正常关闭至少满足：

1. 有处理记录；
2. 有关联业务单据、盘点结果或明确的人工核查说明；
3. 最新一次 V2 运行时间晚于关键处理动作；
4. 填写最终原因、解决方式、操作人和总部确认；
5. 若最新结果仍触发，只能选择“接受例外 / 规则误判 / 主数据问题”，不能标记为“已恢复”。

## 自动与人工边界

系统可以自动：

- 保存首次研判快照；
- 打开并预填业务草稿；
- 监听关联单据状态；
- 单据确认后触发重新研判；
- 对比前后结果并建议关闭或继续。

系统不得自动：

- 修改库存；
- 提交正式订货、收货、报损或调拨；
- 认定责任人；
- 选择接受例外；
- 最终关闭工单。

## 当前实施状态

- 工单交互按“问题摘要 → 本次任务 → 建议动作与执行 → 系统研判过程 → 业务记录 → 人工闭环”组织；基础元数据折叠，不再占据第一屏；
- 建议动作已从技术研判中拆出，每项展示优先级、推荐原因、责任角色、完成状态和带工单上下文的执行入口；
- 工单详情展示当前 V2 结果、库存重建公式、今日/近 3 日证据、证据缺口、决策轨迹和规则状态；
- 新建研判工单保存首次 V2 快照，快照包含来源信号、事实量、证据引用、规则版本、缺失证据和建议动作；
- 工单动作统一携带门店、物料、日期和来源工单，盘点、调拨、订货、收货页面可直接预填；
- 收货确认、调拨签收、关联盘点完成及工单库存动作确认后自动重算，手动重算入口仍保留；每次运行追加快照，不覆盖历史；
- 人工闭环表单已要求最终原因、解决方式、操作人、门店采纳和总部确认；最新 V2 仍触发时禁止选择“已恢复”；
- 页面已将 V2 快照改为按最新优先的重算记录列表；顶部提炼首次到最新的状态、归因与理论库存变化，每条记录可展开查看公式、证据、缺口和决策轨迹，超过 10 条分页展示；
- “尚未解决”可选择重新交由门店、升级总部库存运营或升级主数据治理；每次闭环尝试、重新打开和升级均写入工单时间线与审计记录；
- “主数据问题”会直接建立总部治理任务并保留原工单，等待治理完成后再次重算；
- 新增边界测试覆盖重复证据、单位不一致、到货未入库、实盘有/无、历史不完整、查询失败及恢复门禁。
- 2026-09-17 线上工单链路复测：D1 牛奶、S1 茶叶、T2 半成品奶茶均已建立跟进工单并完成第二次人工重算；首次快照保留、最新快照追加，异常仍触发时“已恢复”均被关闭门禁拒绝。工单面向业务人员统一显示中文规则名，内部枚举仅保留在接口与技术数据中。
- 2026-09-17 D2 全链路模拟发现并修复“规则恢复后原工单仍读取旧异常事实”的问题：台账重算现在会同步刷新已自动恢复信号的最新数量与证据；即使同一物料随后转为 D1 等其他异常，原 D2 工单也能按最新事实保存正确的处理后快照，而新异常继续独立跟进。
