# 库存研判行动编排与工单双端设计 v1

- 版本：v1.0
- 日期：2026-09-21
- 范围：总部库存研判 V3、AI 深度研判、跟进工单、门店移动工作台
- 状态：MVP 实施基线

## 1. 要解决的问题

当前系统已经能输出 V2 规则结论和 AI 深度研判，但“判断”与“执行”之间仍有断点：

1. AI 给出了验证顺序，却不能逐条采纳，也不能形成责任明确的后续动作。
2. 规则建议与 AI 建议各说各话，没有进入同一个执行计划。
3. 总部库存研判中的关联工单会受到移动端登录态影响，错误跳转到门店工作台。
4. 工单容易退化成一段说明文字，缺少“为何做、谁来做、从哪里做、完成后如何验证”的闭环。
5. AI 若直接写库存、建正式单据或关闭工单，会越过必要的人工门禁。

本设计将系统主线统一为：

> 事实包 → V2 确定性研判 → 可选 AI 深度研判 → 人工采纳建议 → 行动计划 → 业务执行与凭证 → V2 重算 → 人工关闭或升级

## 2. 核心原则

### 2.1 一个问题只保留一个持续 Case

同一门店、同一物料、同一规则族在多个营业日重复触发时，追加为 Case 的观察记录，不重复制造多个待办问题。Case 可以关联多次规则快照、AI 分析和历史工单，但同一时间只允许一个活动工单。

### 2.2 V2 是正式裁决，AI 是调查增强

- V2 负责异常是否触发、计算公式、证据状态、规则版本和允许的系统动作。
- AI 负责竞争假设、反证、验证顺序和向门店提问。
- AI 不得直接修改库存、确认收货、签收调拨、建立正式单据、定责或关闭工单。
- AI 输出异常或不可用时，规则建议仍可独立进入行动计划。

### 2.3 规则建议与 AI 建议共用行动计划

用户不需要理解建议来自哪套技术。采纳后统一形成 `InventoryCaseAction`，后续状态、责任人、入口和审计方式一致。

### 2.4 总部与移动端共用工单数据，不共用页面入口

- 总部入口：`/work-order/?portal=hq&id={work_order_id}`
- 门店／加盟商／督导入口：`/work-order/?id={work_order_id}` 或移动工作台内嵌详情
- 两端读取同一工单、行动、凭证、重算与时间线。
- 总部入口允许人工闭环、升级和治理转派；移动端只显示其角色有权执行的动作。

## 3. 页面信息架构

库存研判列表展开后依次显示：

1. **当前结论**：正式引擎、触发规则、计算值、持续营业日、首次和最新观察。
2. **规则建议行动**：V2 生成的白名单动作，可逐条“采纳并编排”。
3. **AI 深度研判**：假设、支持证据、反证、证伪方式、验证顺序；每个步骤均可单独采纳。
4. **跨营业日观察记录**：展示同一 Case 的历史触发与恢复，不再把每日重算误当成新工单。
5. **工单与证据入口**：总部打开关联工单；库存流水、业务单据均携带 Case 和工单上下文。

采纳后的按钮状态改为：

- `已采纳 · 责任人`
- 有系统入口时显示“进入执行”
- 没有活动工单时显示“需要先建立后续工单”，不得静默丢失

## 4. 数据契约

### 4.1 InventoryCaseAction

```json
{
  "id": "ACT-...",
  "inventory_case_id": "IC-...",
  "work_order_id": "OPT-...",
  "source": "rule | ai",
  "source_ref": "事实包+动作ID，或AI分析ID+步骤序号",
  "action_id": "VIEW_TRANSFER | VIEW_RECEIPTS | CREATE_SPOT_COUNT | ASK_STORE ...",
  "title": "核对目标门店是否实际签收",
  "reason": "为什么该动作排在当前顺序",
  "owner": "门店店长 / 区域督导 / 总部运营",
  "mode": "read | draft | manual",
  "status": "proposed | accepted | in_progress | completed | rejected | needs_work_order",
  "execution_url": "/transfers/?store=...&source_case_id=...&source_work_order_id=...",
  "accepted_by": "总部运营",
  "accepted_at": "ISO-8601"
}
```

`source_ref` 是幂等键。同一个 AI 步骤或同一事实包中的规则动作重复点击时，返回已有行动，不重复创建。

### 4.2 允许的动作白名单

| 动作 | 用途 | 系统行为 |
| --- | --- | --- |
| `VIEW_PURCHASE` | 核对订货与在途 | 打开订货列表并带入门店、物料、营业日 |
| `VIEW_RECEIPTS` | 核对收货 | 打开收货列表并带入上下文 |
| `VIEW_TRANSFER` | 核对调拨 | 打开调拨列表并带入上下文 |
| `VERIFY_DESTINATION_ACCEPTANCE` | 核对目标门店签收 | 进入调拨／签收核查 |
| `CREATE_SPOT_COUNT` | 临时盘点 | 建立盘点草稿，仍需人工确认 |
| `VIEW_FLOWS` | 检查库存流水 | 只读查看库存事件 |
| `CREATE_RECEIPT_DRAFT` | 补录收货 | 只建立草稿，不自动确认入库 |
| `CREATE_RESTOCK_DRAFT` | 紧急补货 | 只建立草稿，不自动下单 |
| `ASK_STORE` | 线下询问或补充说明 | 返回工单处理记录表单 |

AI 自然语言步骤必须先映射到上述白名单。无法安全映射时降级为 `ASK_STORE`。

## 5. 状态与闭环

### 5.1 行动状态

1. `proposed`：规则或 AI 提议，尚未采纳。
2. `accepted`：人工已采纳并绑定活动工单。
3. `in_progress`：责任人开始处理。
4. `completed`：已产生处理结果或业务凭证。
5. `rejected`：人工明确不采用并记录原因。
6. `needs_work_order`：Case 暂无活动工单，需要建立后续工单后再执行。

### 5.2 业务动作后的自动重算

以下事件完成后自动追加 V2 快照：

- 收货确认
- 调拨签收
- 盘点完成
- 影响库存的修正流水写入

若规则仍触发，工单不得以“已恢复”关闭；可重新交门店、升级督导、升级总部或转主数据治理。若原问题已关闭后再次发生，保留历史工单并建立新的后续工单，不改写旧结论。

### 5.3 关闭门禁

关闭前至少满足：

1. 有最终原因和解决方式。
2. 有操作人、门店采纳状态和总部确认。
3. 已保存最新 V2 快照。
4. 选择“已恢复”时，最新规则必须不再触发。
5. 选择“接受例外／规则误判／主数据问题”时，必须记录原因和后续责任方。

## 6. 权限边界

- 总部运营：运行 AI、采纳建议、编排行动、查看全量证据、关闭或升级工单。
- 区域督导：处理所属区域的协同／巡店动作，不可修改规则版本。
- 加盟商／门店：执行被分配动作、上传凭证、提交核查结果；不能关闭总部工单。
- 规则引擎：可生成建议和重算快照，不直接执行人工确认动作。
- AI：只提供结构化调查建议，无写业务数据权限。

## 7. MVP 验收标准

1. 总部库存研判的关联工单始终打开总部工单页，不被移动端登录态重定向。
2. 每条 V2 规则建议都能采纳，刷新后仍显示已采纳及执行入口。
3. 每条 AI 验证步骤都能独立采纳，并具有幂等性。
4. 所有业务入口带入门店、物料、营业日、来源 Case 和来源工单。
5. 采纳动作写入工单时间线和系统审计。
6. AI 不可绕过白名单创建任意 URL 或直接写库存。
7. 无活动工单的 Case 不静默创建业务动作，而是明确标记 `needs_work_order`。
8. 收货、调拨签收或盘点完成后，V2 重算能决定恢复、继续处理或升级。

## 8. 后续迭代

本版先完成“采纳并编排”和可执行入口。下一版补充：行动开始／完成接口、责任人改派、拒绝原因、移动端待办状态同步，以及由业务事件自动完成对应行动。它们不改变本文的数据模型与安全边界。
