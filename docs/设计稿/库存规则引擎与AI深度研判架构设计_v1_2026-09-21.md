# 库存规则引擎与 AI 深度研判架构设计

- 版本：V1.0
- 日期：2026-09-21
- 状态：已确认；第一阶段已完成，第二阶段待实施
- 适用范围：D1／D2／S1／T2、持续问题、工单闭环、AI 深度研判

## 1. 设计目标

系统采用“双引擎、同事实、强门禁”架构：

1. 结构化规则引擎负责可重复计算、异常触发、证据缺口、严重程度和关闭门禁；
2. LLM 负责多假设推理、证据解释、追问设计、行动规划和自然语言表达；
3. 两者读取同一个不可变 Fact Packet，避免各自使用不同口径；
4. LLM 不直接写库存、不直接关闭工单、不覆盖结构化规则结果；
5. 所有业务写入继续经过人工确认和既有权限控制。

## 2. 总体结构

```text
销售、库存、订货、收货、调拨、盘点、报损
                    ↓
             Fact Packet 事实包
               ↙           ↘
      确定性规则引擎       AI 深度研判
      触发/阈值/门禁       假设/解释/行动方案
               ↘           ↙
          对照、冲突标记与人工确认
                    ↓
        Observation → Case → Work Order
                    ↓
              执行、重算、闭环
```

## 3. 代码模块边界

```text
src/diagnosis/
├─ index.js                         对外统一入口
├─ contracts.js                     Fact、Result、AIAnalysis 契约
├─ actions.js                       业务动作目录
├─ facts.js                         当前事实构建器
├─ engine/
│  ├─ registry.js                   注册规则、规则族和版本
│  └─ runner.js                     统一执行与结果标准化
├─ lifecycle/
│  └─ inventory-cases.js            跨营业日合并、恢复和复发
├─ d1-engine.js                     D1 理论与实盘差异
├─ d2-engine.js                     D2 负库存
├─ s1-engine.js                     S1 安全库存
├─ t2-engine.js                     T2 销入比
└─ closure.js                       人工闭环门禁
```

`worker.js` 最终只负责 HTTP、鉴权、存储适配和调用应用服务，不再包含规则判断和 Case 状态机。

## 4. 规则引擎约束

规则函数必须是纯函数：相同输入得到相同输出。规则内部禁止：

- 查询 R2、D1 或飞书；
- 创建或关闭工单；
- 修改库存和单据；
- 调用 LLM；
- 读取页面状态；
- 隐式使用当前时间。

统一入口：

```js
evaluateDiagnosisSignal(signal, context)
evaluateRulePacket(ruleCode, factPacket)
```

统一输出包含规则集、规则版本、事实包编号、决策轨迹、证据缺口和建议动作。

## 5. Case 生命周期

持续问题不等同于每日异常信号：

- 同门店、同物料、同单位、同问题族且没有恢复证据时，跨营业日合并；
- 每次规则执行生成不可变 Observation；
- 一个持续问题只允许存在一张未关闭工单；
- 规则恢复后进入验证和人工关闭；
- 已关闭后更晚营业日再次触发，建立新 Case，并记录 `recurrence_of_case_id`；
- 历史信号不再单独要求处理。

## 6. AI 深度研判契约

AI 研判使用手动触发，输入包括：

- 当前 Fact Packet；
- 结构化规则结果和决策轨迹；
- 近 3 日／7 日流水摘要；
- 关联订货、收货、调拨、盘点和报损单据；
- 版本化 Knowhow；
- 当前 Case 与历史闭环记录。

建议保存以下结构：

```json
{
  "ai_analysis_id": "AI-...",
  "inventory_case_id": "ICS-...",
  "based_on_observation_id": "OBS-...",
  "model": "...",
  "prompt_version": "inventory-analysis-v1",
  "hypotheses": [],
  "recommended_steps": [],
  "questions_for_store": [],
  "rule_agreement": "agree|partial|disagree|insufficient",
  "risk_notes": [],
  "generated_at": "..."
}
```

必须分开显示“确定事实”和“AI 推测”。数据重算后，旧 AI 结果标记为基于旧快照，不能自动沿用。

## 7. 实施阶段

### 第一阶段：模块解耦

- 建立规则注册中心和统一 Runner；
- 动作目录独立；
- Case 生命周期迁出 `worker.js`；
- 保持现有阈值、页面和接口结果不变；
- 使用现有保护测试验证等价行为。

实施结果（2026-09-21）：规则注册中心、统一 Runner、动作目录和 Case 生命周期模块已落地；`worker.js` 已改为调用独立模块，原有阈值与业务结果保持不变。

### 第二阶段：AIAnalysis 契约与只读接口

- 补充 AIAnalysis 校验器；
- 建立手动触发接口；
- 保存模型、Prompt、规则版本和事实快照引用；
- 默认不生成业务写入。

### 第三阶段：V3 页面交互

- 在持续问题详情增加“AI 深度研判”；
- 展示规则与 AI 是否一致；
- 支持采纳、部分采纳、不采纳及原因；
- 建议动作跳转现有收货、调拨、盘点和订货流程。

### 第四阶段：Agent 闭环

- 根据缺失证据向门店发起结构化追问；
- 人工确认后创建动作草稿；
- 动作完成自动重算；
- 将最终原因和解决方式沉淀为案例；
- 高频稳定判断再升级为确定性规则。

## 8. 第一阶段验收标准

1. 四条规则只能通过注册中心统一运行；
2. Shadow、正式重算和未来 AI 共用同一 Runner；
3. Case 合并和复发逻辑不再依赖页面代码；
4. 在同一输入快照下，持续问题的数量和状态与改造前保持不变；动态同步产生的新观察按问题族正常新增或合并；
5. 主回归、规则测试、采购收货和角色工单回归全部通过。
