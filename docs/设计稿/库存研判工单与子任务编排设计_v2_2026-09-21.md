# 库存研判、主工单与子任务编排设计 v2

- 版本：v2.0
- 日期：2026-09-21
- 状态：讨论稿 / 下一轮实现基线
- 替代范围：修正《库存研判行动编排与工单双端设计 v1》中“研判建议可脱离工单直接采纳并执行”的设计

## 1. 修正后的核心认识

库存研判、工单和任务不是同一个对象：

1. **研判 Case** 说明系统发现了什么、证据是什么、是否值得关注。
2. **主工单** 说明运营决定对哪个问题持续跟踪，并对最终结果负责。
3. **工单子任务** 说明为解决主工单，需要谁在何时完成哪一个具体动作。
4. **业务单据** 是子任务执行过程中创建或关联的订货、收货、调拨、盘点、报损等凭证。
5. **V2 重算快照** 验证业务动作是否真的改变了异常状态。

因此，正确链路是：

```text
数据与规则触发
  → 研判 Case
  → 运营查看规则结论 / AI 分析
  → 忽略、继续观察，或创建主工单
  → 从建议清单中选择并生成工单子任务
  → 责任人执行并关联业务单据 / 线下结果
  → 自动重算 V2
  → 主工单关闭、重新打开或升级
```

当前阶段由运营用户决定是否创建工单。未来 Agent 可以按授权策略自动创建工单和子任务，但仍需审计、权限与关闭门禁。

## 2. 领域对象与边界

### 2.1 InventoryCase：持续问题

职责：聚合同一门店、物料和规则族跨营业日的观察。

包含：

- 异常来源、规则代码和规则版本；
- 首次与最新营业日；
- 事实包、计算公式和证据缺口；
- V2 结论；
- AI 分析历史；
- 建议候选；
- 关联主工单历史。

Case 不承担：责任人流转、到期时间、任务执行状态和最终验收。

Case 建议状态：

- `new`：新发现，待运营查看；
- `reviewed`：已查看，尚未决定是否跟踪；
- `observing`：继续观察，暂不建工单；
- `tracked`：已有活动主工单；
- `dismissed`：人工认定不需要跟踪，需记录原因；
- `recovered`：规则重算后恢复。

### 2.2 DiagnosisSuggestion：研判建议候选

建议由规则或 AI 产生，但尚不是任务。

```json
{
  "id": "SGT-...",
  "inventory_case_id": "ICS-...",
  "source": "rule | ai",
  "source_ref": "事实包+动作，或AI分析+步骤",
  "action_id": "VIEW_TRANSFER",
  "title": "核对调拨与目标门店签收",
  "reason": "为何建议做这件事",
  "recommended_owner_role": "store_manager",
  "execution_mode": "read | manual | draft",
  "status": "proposed | selected | converted | rejected | stale"
}
```

关键约束：

- `proposed` 只表示候选，不表示已经有人负责。
- 没有主工单时，页面只能“选择纳入拟建工单”，不能“进入执行”。
- 新事实包或新 AI 分析产生后，旧建议可标记为 `stale`，但不得删除审计历史。

### 2.3 WorkOrder：主工单

主工单是问题闭环的唯一责任容器。

```json
{
  "id": "OPT-...",
  "inventory_case_id": "ICS-...",
  "title": "茶叶安全库存与补货核查",
  "problem_statement": "经过运营确认，需要持续跟踪的问题",
  "objective": "本工单完成后应达到的结果",
  "owner_role": "hq_operations",
  "owner_account_id": "ACC-...",
  "assigned_org_id": "STORE001 | REGION-... | HQ",
  "priority": "high | medium | low",
  "due_at": "ISO-8601",
  "status": "draft | open | in_progress | pending_verification | closed | escalated",
  "diagnosis_snapshot_id": "RUN-...",
  "created_by": "ACC-..."
}
```

规则：同一 Case 同一时间只允许一个活动主工单；已关闭工单保留不改写。问题复发或关闭后仍未解决时建立后续工单，并通过 `previous_work_order_id` 关联。

### 2.4 WorkOrderItem：工单子任务

子任务必须依附主工单，是实际的编排单位。

```json
{
  "id": "WOI-...",
  "work_order_id": "OPT-...",
  "suggestion_id": "SGT-...",
  "title": "联系目标门店确认是否签收",
  "action_id": "VERIFY_DESTINATION_ACCEPTANCE",
  "task_type": "manual_check | business_document | read_only_review | field_visit",
  "owner_role": "store_manager | area_supervisor | hq_operations",
  "owner_account_id": null,
  "assigned_org_id": "STORE001",
  "due_at": "ISO-8601",
  "depends_on": [],
  "status": "todo | accepted | in_progress | pending_review | completed | rejected | cancelled",
  "execution_url": "/transfers/?...",
  "evidence_requirements": ["调拨单号", "目标门店确认结果"],
  "result_note": null,
  "completed_at": null
}
```

“采纳建议”的真实含义应改为：

> 将建议转换为当前主工单下的一个子任务。

它不应再创建一个漂浮在工单之外的行动记录。

### 2.5 BusinessDocument：业务单据与证据

盘点计划、订货草稿、收货单、调拨单和报损单通过 `source_work_order_id` 与 `source_work_order_item_id` 双重关联：

- 主工单用于汇总完整闭环；
- 子任务用于判断哪一项动作已经完成。

业务单据状态变化可自动推动子任务：

- 盘点完成 → 对应盘点子任务进入 `pending_review/completed`；
- 收货确认 → 对应收货子任务完成并触发 V2 重算；
- 调拨签收 → 对应调拨子任务完成并触发 V2 重算；
- 线下询问 → 必须填写结果后才能完成。

## 3. 页面与交互

### 3.1 研判页

研判页只做“发现、解释和决定是否跟踪”。

#### 没有活动工单

页面显示：

- 当前规则结论；
- AI 深度研判；
- 建议候选清单，使用复选框；
- `创建跟进工单` 主按钮；
- `继续观察`、`不需要跟踪` 次级动作。

点击“创建跟进工单”进入确认层：

1. 工单标题和问题描述自动带入；
2. 可选择责任组织、主负责人、优先级和期限；
3. 已勾选建议显示为“拟生成子任务”；
4. 提交后一次性创建主工单及所选子任务；
5. 成功后跳转总部工单详情。

#### 已有活动工单

顶部显示：`已由工单 OPT-... 跟踪`。

建议候选按钮改为：

- 尚未加入：`加入工单任务`；
- 已转换：`已加入 · WOI-...`；
- 已过期：`建议已过期`；
- 主工单已关闭：`创建后续工单`，不能追加到历史工单。

### 3.2 总部工单详情页

建议结构：

```text
问题与目标
├─ 原始研判快照
├─ 最新 V2 状态
└─ 主负责人、责任组织、期限、优先级

执行计划
├─ 待办子任务
├─ 处理中
├─ 待验收
└─ 已完成

待采纳建议
└─ 新规则 / AI 建议，可追加为子任务

业务单据与证据
└─ 盘点、订货、收货、调拨、报损、附件和人工记录

重算与闭环
└─ 处理前后 V2、关闭门禁、重新打开或升级
```

新增处理记录只是时间线备注，不等于子任务完成。子任务必须有明确完成动作和证据。

### 3.3 移动端

门店、加盟商和督导只看分配给自己的子任务，不直接操作总部研判 Case。

移动端入口展示：

- 主工单摘要；
- 我的子任务；
- 执行入口；
- 所需凭证；
- 提交处理结果；
- 问门店助手。

总部工单 URL 必须显式使用：

```text
/work-order/?portal=hq&id=OPT-...
```

移动端入口使用：

```text
/work-order/?id=OPT-...
```

两端共享数据，不共享默认导航和权限动作。

## 4. 创建与编排接口

### 4.1 创建主工单并选择初始建议

```text
POST /api/inventory-cases/{case_id}/work-orders
```

请求：

```json
{
  "title": "茶叶安全库存与补货核查",
  "objective": "确认真实缺货风险并形成可执行补货方案",
  "owner_account_id": "ACC-HQ-WANG",
  "assigned_org_id": "STORE001",
  "priority": "high",
  "due_at": "...",
  "suggestion_ids": ["SGT-1", "SGT-2"]
}
```

服务端应在一次保存中：

1. 校验 Case 没有活动主工单；
2. 保存最新研判快照引用；
3. 创建主工单；
4. 将选中建议转换成子任务；
5. 写入审计；
6. 返回工单和子任务。

### 4.2 给已有工单追加建议

```text
POST /api/work-orders/{work_order_id}/items/from-suggestion
```

按 `work_order_id + suggestion_id` 幂等。只有活动工单可追加。

### 4.3 人工增加子任务

```text
POST /api/work-orders/{work_order_id}/items
```

支持运营自行增加线下询问、督导巡店、单据核查等任务，并保留创建人和原因。

## 5. 规则与 AI 的位置

- V2 规则引擎输出确定性建议候选，不创建主工单或子任务。
- AI 输出解释、竞争假设和建议候选，不直接写工单。
- 运营负责在研判页决定是否创建工单及选择初始任务。
- Agent 自动化属于后续能力：按授权策略代替运营完成“创建工单 + 转换建议”，但必须保留 `created_by=agent`、规则版本、Prompt 版本、理由和人工复核状态。

自动化成熟度：

1. M0：运营手动创建主工单并选建议。
2. M1：系统预选任务，运营一次确认。
3. M2：高置信规则自动建草稿工单，运营发布。
4. M3：Agent 在白名单场景自动发布工单和子任务，人工只处理例外。

## 6. 主工单关闭门禁

关闭前校验：

1. 所有必需子任务已完成、取消或明确拒绝；
2. 每个必需子任务具备对应结果或凭证；
3. 已保存最新 V2 快照；
4. “已恢复”必须由最新 V2 不再触发支持；
5. 未恢复时必须选择重新交门店、升级督导、升级总部或转治理；
6. 最终原因、解决方式、操作人、门店采纳和总部确认完整。

## 7. 当前实现的迁移处理

现有 `inventoryCaseActions` 不再视为正式执行计划，迁移为 `DiagnosisSuggestion` 的选择／转换历史：

- 有活动工单且记录已产生执行入口：转换成对应 `WorkOrderItem`；
- 没有活动工单：恢复为 `proposed/selected`，不允许进入执行；
- 已关闭工单：只保留历史，不追加子任务；
- 页面移除无工单情况下的“采纳并编排”。

## 8. MVP 验收场景

1. 运营打开一个没有工单的 S1 Case，选择“核对在途”和“建立补货草稿”，创建主工单后得到两个子任务。
2. 门店只看到分配给自己的补货子任务，总部继续看到完整主工单。
3. 建立订货草稿后，补货子任务仍未完成；提交或达到约定状态后才进入待验收。
4. 收货确认后对应子任务完成，系统自动追加 V2 快照。
5. V2 仍触发时，主工单关闭门禁阻止“已恢复”。
6. 运营升级督导并增加巡店子任务，责任流转写入时间线。
7. 同一建议重复加入时不产生重复子任务。
8. 总部首页、库存研判页和工单详情页的总部入口均不跳转到移动端。
