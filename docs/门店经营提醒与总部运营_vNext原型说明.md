# 门店经营提醒与总部运营 vNext 原型说明

> 状态：独立交互原型，不连接业务接口，不进入现有导航，不部署线上
>
> 原型路径：`prototypes/operations-reminders-vnext/index.html`

## 1. 本轮验证的问题

原型不验证视觉风格是否最终定稿，而验证以下产品假设：

1. 门店是否能在 3 秒内知道今天最重要的事情；
2. 普通提醒是否可以限制为 1～3 条，而不是展示所有异常；
3. LLM 是否能把规则和证据解释为门店愿意执行的动作；
4. 门店的“稍后提醒、与实际不符、需要帮助”是否能成为有效反馈；
5. 总部是否可以先看跨门店问题簇，再下钻独立工单；
6. 数据质量问题是否应与门店执行问题分开；
7. 提醒是否始终引用现有工单，而不是产生第二套业务状态。

## 2. 门店端信息结构

门店端默认只展示三层：

```text
今天最重要：最多 1 条
需要你处理：普通提醒最多 3 条
今日经营简报：每天 1 条
```

“今天最重要”使用影响、紧迫、可执行性和可信度排序。高影响但门店无法处理的数据问题不推给门店，直接进入总部数据质量队列。

提醒卡不直接使用 D2、D1、S1、T2 等技术枚举，而显示：

- 发生了什么；
- 为什么值得今天处理；
- 系统核对过哪些证据；
- 建议先做什么；
- 处理后系统如何验证。

## 3. LLM 交互

点击“问门店助手”打开解释层。LLM 的输入必须来自冻结的结构化上下文：

- 当前工单；
- 最新 V2 结果；
- 证据与缺失证据；
- 可执行动作；
- 门店角色与语言；
- 规则和文案版本。

LLM 允许解释、追问、合并信息和预填草稿，不允许修改规则结论、自动提交单据、改变库存、自动定责或关闭工单。

## 4. 总部端信息结构

总部端用漏斗说明为什么没有展示所有信号：

```text
原始信号 → 合并问题 → 可执行事项 → 总部需介入
```

首页只保留四类内容：

1. 今日需干预；
2. 跨门店共性问题；
3. 执行与闭环；
4. 数据质量。

每个总部聚合问题引用若干独立门店工单。处理主数据或供应链问题后，对关联工单批量触发 V2 重算，但不直接批量关闭工单。

## 5. 与现有 Demo 的关系

保留现有：

- D2/D1/S1/T2 规则；
- V2 快照与历史；
- 跟进工单；
- 订货、收货、调拨、盘点和库存流水；
- 业务动作后的自动重算；
- 人工闭环、重开和升级门禁。

原型新增的是展示投影和交互，不新建平行数据源：

```text
现有异常与工单事实
→ 通知选择与优先级
→ 门店/督导/总部不同投影
→ 用户动作仍回到原工单和业务单据
```

## 6. 评审时需要拍板

1. 门店普通提醒上限是否采用每天 3 条；
2. “今天最重要”是否允许没有事项；
3. 门店可选择的反馈项；
4. 门店首页是否保留独立“提醒”Tab，还是并入“任务”；
5. 总部默认按区域、物料还是问题类型聚合；
6. 数据质量队列的责任角色；
7. LLM 解释是否默认展开；
8. 哪些情况允许立即推送飞书，哪些只进入日报。

## 7. 确认后的实现顺序

1. 冻结通知、受众和投递数据契约；
2. 给现有工单事件增加只读通知投影；
3. 实现门店提醒列表和详情；
4. 实现总部问题聚合与下钻；
5. 接入去重、抑制、SLA 与升级；
6. 最后将飞书作为统一提醒的投递通道；
7. 用 D2 主链和 D1/S1/T2 补充案例做保护测试。
