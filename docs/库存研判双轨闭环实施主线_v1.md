# 库存研判双轨闭环实施主线 v1

> 状态：项目当前实施基线  
> 更新日期：2026-09-17  
> 适用范围：STORE001 库存研判 MVP  
> 上游参考：`references/` 中的豆包架构、规则包、Knowhow 与验收场景

## 1. 已确认的产品方向

项目采用两条互补但不互相覆盖的研判轨道：

1. **规则研判 MVP**：使用确定性事实和版本化决策树，产出可解释、可复算的研判案例。
2. **AI 研判 MVP**：由用户手动触发，读取同一份事实快照和精确匹配的 Knowhow，补充假设、反证、缺失证据与行动建议。

两条轨道最终进入同一套工单与闭环机制：

```text
业务数据
  → 统一事实包
    → 决策树规则 → 规则研判 ┐
    → Knowhow + LLM → AI研判 ├→ 人工确认 → 跟进工单
                                      → 业务单据/凭证
                                      → 库存重算
                                      → 人工闭环或重新排查
```

规则是事实基线，AI 是人工触发的第二意见。AI 不覆盖规则结论、不直接写库存、不自动定责、不自动闭环。

## 2. 共同语言与名称

为避免页面、代码和豆包文档使用不同名称，统一采用以下称谓：

| 中文名称 | 代码名称 | 含义 |
|---|---|---|
| D2 负库存 | `D2_NEGATIVE_STOCK` | 理论期末低于允许的负库存容差 |
| D1 账实差异 | `D1_STOCK_VARIANCE` | 有效实盘与同一截止时点理论库存的差异超过容差 |
| S1 补货风险 | `S1_REPLENISHMENT_RISK` | 可用库存或库存覆盖低于门店安全需求 |
| T2 供耗失衡 | `T2_SUPPLY_CONSUMPTION_IMBALANCE` | BOM 换算后的物料消耗与同周期入库明显失衡 |
| 研判案例 | `diagnosis_case` | 一次规则触发、证据、假设、动作和版本的完整记录 |
| 事实包 | `fact_packet` | 某门店、营业日、物料在指定截止时点的结构化事实 |
| 规则运行轨迹 | `decision_trace` | 决策树每个节点的输入、结果和证据引用 |
| AI 复核 | `ai_review` | 对冻结事实包进行的手动 LLM 第二意见 |
| 跟进工单 | `work_order` | 承接人工调查、业务动作、单据和闭环的执行载体 |

页面可继续使用简短名称 D2/D1/S1/T2，数据库和接口使用稳定代码名称，并保留旧代码映射以兼容现有数据。

## 3. 统一事实层

规则和 AI 必须读取同一份事实包，页面不得各自重新推断。

事实包最少包含：

- 门店、营业日、物料、基础单位、计算截止时间；
- 期初、收货、调拨入、调拨出、报损、盘盈、盘亏、销售 BOM 消耗；
- 理论期末、最近有效实盘、实盘截止时间、账实差异；
- 今日、近 3 日、近 7 日聚合；
- 盘点策略、今日盘点任务状态；
- 安全库存、物料关键性、关联销售 SKU；
- 订货、在途、目标门店签收等数据的接入状态；
- 每项事实的来源、时间和证据编号。

事实值必须区分：

| 状态 | 含义 |
|---|---|
| 数值 `0` | 已成功查询，确认没有业务数量 |
| `null` | 当前系统尚未接入该数据 |
| `unknown` | 数据理论上可用，但本次查询失败或状态不明 |
| `not_applicable` | 该物料或场景不适用 |

系统不能把“未接入收货单”表述成“确认没有收货”。

## 4. 研判输出模型

每个研判案例分别记录三种状态：

1. **异常事实状态**：是否确认触发 D2/D1/S1/T2。
2. **原因证据状态**：首要原因是有证据、高度疑似、证据不足还是已排除。
3. **实物确认状态**：有效实盘、待盘点或实盘已过期。

五档证据名称统一为：

| 代码 | 页面名称 | 说明 |
|---|---|---|
| `confirmed` | 有直接证据 | 事实链能够支持当前假设；不等于对人员定责 |
| `excluded` | 已排除 | 现有证据排除当前假设，继续下一分支 |
| `suspect` | 高度疑似 | 有支持证据，但仍需要人工或单据确认 |
| `insufficient` | 证据不足 | 关键数据未接入、缺失或查询失败 |
| `pending_count` | 待盘点 | 必须取得有效实盘才能继续 |

每个案例输出：异常来源、首要排查位置、候选原因排序、支持证据、反证、缺失证据、推荐动作、规则版本、运行轨迹和重算时间。

## 5. 工单承接原则

工单是研判的执行过程，不是只有一句通用说明的任务卡。创建工单时冻结研判快照，至少继承：

- 来源案例、规则类型、触发条件和规则版本；
- 建单时库存公式和今日/3日/7日证据；
- 首要假设、备选假设、已排除项、缺失证据；
- 有顺序的建议动作和可用系统入口；
- 建单时库存状态与后续最新状态的对比。

动作采用稳定 `action_id`，由动作注册表解析为真实页面、草稿或人工步骤。功能未接入时必须显示“数据未接入”和人工替代方案，不能伪装成已完成查询。

工单状态暂定：

```text
待处理 → 门店处理中 → 待总部确认 → 已闭环
                                    ↘ 重新打开
```

闭环必须人工确认并记录最终原因、解决方式、关联单据、处理人、门店是否采纳、总部确认、调整前后结果及是否需要修正规则/BOM/主数据。

## 6. AI 研判 MVP

AI 研判由案例页或工单页手动触发。输入由系统组装，不允许模型自行猜测数据库事实：

- 冻结事实包；
- 规则研判结果和完整运行轨迹；
- 今日/3日/7日证据；
- 相关单据、流水、盘点和工单记录；
- 根据“规则类型 + 物料类别 + 证据状态 + 首要位置”精确匹配的 Knowhow 片段；
- 当前系统实际支持的动作清单。

AI 输出使用结构化 Schema：

- `agreement`：同意、部分同意、不同意、证据不足；
- 首要假设和备选假设；
- 每个假设的证据引用与反证；
- 缺失证据和最小追问；
- 建议动作 ID；
- 面向用户的自然语言总结。

每次 AI 复核保存模型、Prompt 版本、知识版本、规则版本、事实快照哈希、耗时、成本、输出和人工采纳结果。第一阶段不用向量数据库；知识通过精确索引选取。闭环案例足够多后再评估向量检索。

## 7. Agent 闭环方向

长期目标不是自动判案，而是受控地推进问题完成。状态机建议为：

```text
DETECTED
→ EVIDENCE_NEEDED
→ WORK_ORDER_DRAFT
→ CONFIRMED
→ EXECUTING
→ VERIFYING
→ CLOSED / REOPENED
```

Agent 第一阶段可以自动选择下一步、打开页面、预填草稿、请求证据、监控状态和触发重算；库存写入、正式单据提交、责任确认、外部推送和最终闭环仍需人工确认。

## 8. 分阶段实施与验证

### Phase 0：规则资产治理

1. 建立事实包、决策树、研判案例和动作注册表 Schema。
2. 将 `references` 标记为上游草案快照，不在运行时直接执行。
3. 修订量纲、状态语义和自动定责/自动推送问题。
4. 固化现有回归为不退化基线，并为 V1 行为、数据契约和 V2 规则增加独立单元测试。

验收：JSON Schema 校验通过；同一事实包重复执行得到完全相同结果；旧页面和现有业务流程不退化。

### Phase 1：D2 垂直跑通

1. 建事实聚合器和通用决策树执行器。
2. 只先实现 D2，输出完整轨迹和动作。
3. 研判案例完整传入工单。
4. 工单动作连接流水、调拨、盘点及可用单据页面。
5. 业务数据变化后重算，并由人工填写最终解决方式闭环。

验收：黑糖珍珠案例能明确指出 `12000 - 13000 - 90 = -1090g`，调拨出为第一贡献项，无入库为辅助证据，实物状态为待盘点；修正调拨或提交盘点后能重算并建议闭环。

### Phase 2：复制到 D1/S1/T2

逐棵树完成事实、节点、动作和边界测试。T2 必须先将销售通过 BOM 转成同单位物料消耗；D1 必须对齐实盘与理论截止时间；S1 必须考虑库存覆盖和在途状态，不能只比较单一阈值。

验收：四类规则分别覆盖主路径、反例、缺数据、单位错误、重复流水和数据延迟。

### Phase 3：手动 AI 研判

1. 建立 Knowhow 精确索引和 AI 输入快照。
2. 在研判案例中增加手动 `AI 复核`。
3. 规则和 AI 并排显示差异。
4. 人工可采纳建议生成工单草稿，但不能由 AI 直接执行。

验收：模型只能引用输入中的证据编号；缺少收货数据时明确说“未接入/未知”；重复运行保留独立记录；AI 不产生库存写入。

### Phase 4：受控 Agent

将工单、单据、重算和人工确认编排成状态机，先自动推进证据请求和草稿，不开放自动库存写入与自动闭环。

## 9. 双方协作约定

- `references/`：豆包/飞书侧交付快照，保留原文和原始版本。
- `docs/`：项目当前有效设计、审阅结论、实施状态和测试报告。
- `src/diagnosis/`（实施后）：运行时有效规则和执行代码。
- 豆包新增行业规则时，应提供来源、适用条件、反例、所需数据和建议动作。
- Codex 接入前完成 Schema、量纲、数据可用性、安全边界与回归验证。
- 未进入“已启用”清单的规则均为草案，不能影响线上库存和工单。
- 每个研判和 AI 复核都记录规则/知识/Prompt 版本，保证后续可复盘。

## 10. 当前第一步

从 D2 黑糖珍珠案例开始，先建立最小完整闭环，不同时铺开四棵树：

1. 定义事实包 Schema。
2. 固定黑糖珍珠事实夹具。
3. 编写 D2 决策树 v1。
4. 输出运行轨迹和动作 ID。
5. 将完整结果带入工单。
6. 用调拨修正、实盘有货、实盘无货三种结果分别重算。
7. 人工填写闭环方式。
8. 全链路通过后再抽象并复制。

- 接口已核对 `writable=false`、`creates_work_orders=false`；待用户完成人工页面对照后，才考虑将 D2 V2 快照接入正式工单。
