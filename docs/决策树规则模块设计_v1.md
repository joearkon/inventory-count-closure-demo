# 决策树规则模块设计 v1

> 本文定义规则 MVP 的代码边界和 D2 首条垂直链路。`references` 中的 JSON 是上游草案输入，不是运行时可直接执行的规则。

## 2. 决策树节点

MVP 只允许以下受控节点：

| 类型 | 用途 |
|---|---|
| `condition` | 比较已经标准化的事实字段 |
| `calculate` | 使用白名单公式计算指标 |
| `rank` | 按数量贡献、证据强度和业务优先级排序候选原因 |
| `require_evidence` | 将缺失字段加入待补证据 |
| `exclude` | 记录某假设被排除及其证据 |
| `suggest_action` | 输出动作注册表中的 `action_id` |
| `set_status` | 设置异常、原因或实物确认状态 |
| `stop` | 结束当前分支 |

规则 JSON 不允许自由 JavaScript、SQL 或 `eval` 字符串。所有比较符、计算器和动作 ID 都由代码白名单解释。

## 3. 规则运行结果

每个节点都生成可审计轨迹：

```json
{
  "node_id": "D2-CONTRIBUTOR-001",
  "type": "rank",
  "result": "transfer_out",
  "message": "调拨出库 13000g 是负库存最大贡献项",
  "evidence_refs": ["BALANCE-001", "FLOW-TRANSFER-001"]
}
```

运行失败时不得返回猜测结果，应记录 `rule_error` 并保持旧研判案例可读。

## 4. D2 v1 决策路径

### 4.1 触发

只处理：

```text
theoretical_closing_qty < negative_tolerance
```

“库存为零仍有销量”和“库存超过安全库存十倍”不属于 D2，后续另设信号，不混入负库存。

### 4.2 调查步骤

1. 校验期初、流水和 BOM 单位是否可以统一。
2. 重建库存等式并记录每个贡献项。
3. 按负向数量绝对值排序最大贡献项。
4. 检查最大贡献项是否异常大、重复、单位可疑或超过动作前可用库存。
5. 查询今日、近 3 日、近 7 日所有可能入库动作。
6. 检查物料盘点策略、今日任务和最近有效实盘。
7. 判断实际缺货风险和关联销售 SKU 影响。
8. 输出首要假设、备选假设、缺失证据和动作顺序。

### 4.3 黑糖珍珠基准案例

```text
期初 12000g
收货 0g
调拨入 0g
调拨出 13000g
报损 0g
销售 BOM 消耗 90g
理论期末 -1090g
实盘未知
```

期望输出：

- 异常事实：D2 已确认；
- 第一贡献项：调拨出 13000g；
- 首要排查：调拨数量、单位、重复出库和目标门店签收；
- 辅助证据：近 3 日没有已知收货或调拨入；
- 实物状态：待盘点；
- 原因状态：高度疑似，不能直接定责；
- 动作顺序：查看调拨单 → 核对目标签收 → 下发临时盘点 → 根据实盘决定补货或账务修正。

## 5. D2 首批测试矩阵

| 场景 | 输入变化 | 期望首要判断 | 期望动作 |
|---|---|---|---|
| 大额调拨出 | 调拨出超过期初 | 调拨数量/单位/签收高度疑似 | 查调拨、查签收、盘点 |
| 重复调拨 | 同外部单号和明细重复 | 重复记账高度疑似 | 查看重复流水、撤销草稿 |
| 到货未入库 | 有到货凭证、无有效收货流水 | 收货漏录高度疑似 | 建收货补录草稿 |
| 实盘有货 | 理论为负、实盘为正 | 账面差异，不是实际缺货 | 查单据后按实盘调整 |
| 实盘无货 | 理论为负、实盘为零 | 实际缺货已确认 | 紧急补货/调拨建议 |
| 单位错误 | `kg/g` 换算异常 | 主数据或录入单位异常 | 查看单位配置、建立治理工单 |
| 数据未接入 | 订货和到货为 `null` | 证据不足，不得表述为无订货 | 人工确认/等待接入 |
| 查询失败 | 收货来源为 `unknown` | 暂停原因确认 | 重试查询、保留旧案例 |
| 小额容忍 | 仅轻微负数且在容忍范围 | 不触发 D2 | 保留观察日志 |
| 修正后复算 | 撤销错误调拨后库存恢复 | 异常已解除，等待人工闭环 | 填写解决方式、确认关闭 |

## 6. 后续三棵树的进入条件

- D1：先完成盘点截止时间、实盘有效性和物料差异容忍配置。
- S1：先完成安全库存、库存覆盖、关键原料和在途数据状态定义。
- T2：先完成销售 SKU 通过 BOM 转换为同基础单位物料消耗，禁止直接用杯数除以 kg/L 入库量。

## 7. 版本与回滚

每份有效规则包含：

- `ruleset_id`
- `rule_version`
- `effective_from`
- `schema_version`
- `content_checksum`
- `source_reference`
- `approval_status`

研判案例保存当次规则版本和事实快照哈希。更新规则只影响后续重算，不能静默改写旧案例的历史判断。
