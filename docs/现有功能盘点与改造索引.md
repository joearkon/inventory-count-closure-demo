## 1. 如何使用这份索引

每次开始需求、排查问题或恢复项目上下文时，先按以下顺序判断：

1. 在“页面入口”找到用户实际操作的位置；
2. 在“业务能力”确认功能是已实现、部分实现还是仅有方案；
3. 在“数据与外部集成”确认数据来源、营业日和写入边界；
4. 在“关键 API”找到服务端入口；
5. 在“测试索引”找到已有保护用例，再实施改造；
6. 改造完成后更新本文件的状态、限制和对应文档。

状态定义：

- **已实现**：线上 Demo 有页面和服务端能力，能够形成真实的 Demo 状态变化；
- **部分实现**：主链路可演示，但仍有数据、权限、渠道或边界缺口；
- **原型/方案**：只有交互稿或设计文档，不得对外宣称已经上线；
- **暂缓**：已明确不属于当前 MVP。

库存公式：

```text
理论期末 = 有效期初 + 收货 + 调拨入 - 调拨出 - 报损 - Σ(销售 SKU × BOM 用量)
```

规则范围固定为：

- D2：理论负库存；
- D1：理论库存与实盘差异；
- S1：低于安全库存；
- T2：销售/入库关系异常。

## 4. 移动工作台功能

移动端保持三个核心区域，不建设独立“异常中心”：

| 区域 | 能力 | 状态/限制 |
|---|---|---|
| 任务 | 查看本人/本店需要处理的工单和快速任务；进入移动端详情；开始核对、接受并记录、补证、提交结果 | 已实现基础闭环；督导转派和跨区域批量任务仍需加强 |
| 运营 | 订货、收货、调拨、盘点、报损/报废、查库存 | 已实现操作入口；建议订货、成本/毛利经营指标仍是后续能力 |
| 助手 | 保留对话式门店助手；支持库存查询、多商品查询、草稿动作和提交前确认 | 已实现基础对话；不是自主 Agent，所有写入仍需人工确认 |

移动端公共能力：

- 显示营业日、当前账号、门店范围和上级督导；
- 门店员工只看授权门店，督导可切换授权范围内门店；
- 底部导航和输入区适配手机滚动；
- 语音支持中文、English、Bahasa Indonesia 自动识别及设置入口；
- 工单在移动端打开移动详情，不跳往总部 PC 后台；
- 订货、收货、盘点和调拨动作可携带来源工单、门店、物料和营业日上下文。

## 5. 工单与库存闭环

当前可演示的闭环主线：

```text
飞书销售同步
  → 销售 × BOM 形成物料消耗
  → 规则识别 D2/D1/S1/T2
  → 创建跟进工单并保存 V2 快照
  → 门店/督导核对证据
  → 订货、收货、调拨签收或盘点
  → 系统自动重算
  → 首次与最新快照对比
  → 人工填写最终原因、解决方式、操作人、采纳状态
  → 关闭门禁；未解决则重新打开或升级
```

已实现的关键约束：

- 工单保存异常来源、公式、证据、规则版本、缺失证据和建议动作；
- V2 多次重算使用历史列表和详情，不在页面无限并排堆叠；
- 收货确认、调拨签收和盘点完成触发重新研判；
- 关闭前检查最终原因、解决方式、操作人与采纳/确认状态；
- “仍未解决”不能伪装闭环，必须重新打开或升级；
- 所有库存写入均保留来源单据和操作记录。

## 6. 数据来源与边界

| 数据 | 当前来源 | 是否真实 | 写入边界 |
|---|---|---|---|
| 飞书销售 | Base 门店销售明细 | 真实只读 | Worker 每 10 分钟读取到 R2，不回写 Base |
| Brown Sugar BOM | 飞书 Base + 已验证快照回退 | 6 个品牌 SKU 为真实白名单 | 完整性门禁失败时不使用残缺实时 BOM |
| 商品/物料主档 | 系统主档 + 飞书分类/关联 | 混合 | 必须显示来源和数据分类 |
| 期初库存 | 系统初始化/盘点 | Demo 业务状态 | 必须属于明确营业日，不从历史飞书数据静默覆盖 |
| 收货、报损、调拨 | 系统 R2 事件 | Demo 业务数据 | 人工确认后入账；当前不伪装为飞书正式事件表 |
| 经营 KPI、价格、支付 | 尚未形成完整可靠数据 | 未完成 | 不展示无法解释的“潜在损失”等伪 KPI |
| 28 日模拟数据 | 待建设 | Mock | 必须标记 `data_origin=mock`、`scenario_id`、`dataset_version` |

营业日是所有销售、库存、任务、简报和工单的一级字段。自然日上传时间与营业日不能混用。

- 正式 AI 研判页面、LLM 第二意见、交叉验证和 AI Agent 自主闭环尚未完成；

- 消息中心的站内阅读/确认状态与飞书投递状态尚未完全统一。
