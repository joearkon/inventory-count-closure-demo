# MOMOYO 实施诊断与下一阶段产品方案 v1

> 状态：讨论稿，不改变现有 Demo 行为
>
> 日期：2026-09-18
>
> 范围：真实业务数据接入、建议订货、门店经营提醒、总部运营聚合
> 关联文档：《订货与收货MVP_v1.md》《总部运营与门店经营提醒_MVP设计_v1.md》《库存研判闭环设计_v1.md》

## 1. 结论

当前 Demo 已经证明“异常研判 → 工单 → 业务动作 → V2 重算 → 人工闭环”可以运行，下一阶段不应继续横向增加更多页面和规则。优先级应调整为：

1. 先建立可计算、可追溯的数据事实；
2. 用销售和 BOM 理论消耗做第一版订货参考；
3. 将少量高价值事项投影成门店经营提醒；
4. 总部只看聚合风险、执行进度和数据质量；
5. 数据可信后再展示库存金额、理论毛利和更精确的建议订货量。

实施价值不是“再建一个库存系统”，而是在 ICCPOS、供应链和门店人工动作之间建立诊断与执行闭环。系统必须明确区分：真实为零、没有记录、暂未接入、查询失败和数据不可信。

## 2. 本次样本与限制

本次只读分析用户提供的三份 ICCPOS 页面导出，分别覆盖订货、商品报废和门店调拨。仓库文档不保存真实门店名称、人员、单号和金额；原始文件只作为本地分析依据。

前次 ICCPOS 只读查看还看到销售日报、门店库存和门店订货列表。其中门店库存存在大量 `999.999` 样式值，说明部分记录可能为占位、初始化或测试数据；订货记录中也出现 `dummy1` 操作人。

这些材料足以识别实施风险，但不足以评价某一家门店经营好坏。正式诊断至少需要连续 28 个完整营业日的销售、商品、BOM、订货、收货、调拨、盘点和报损数据，并完成门店、商品、物料和单位映射。

## 3. 从真实单据看到的问题

### 3.1 订货单

样本是一张已完成的单物料订货单，包含订货人，但操作人仍显示为测试账号 `dummy1`；明细有商品编码、包装规格、订货单位、价格、数量和小计。

主要问题：

- `dummy1` 不能作为生产审计身份；
- 金额未携带币种、含税口径和价格生效时间；
- 未看到供应商、预计到货、付款状态、发货状态和关联收货；
- “已完成”不能说明是已提交、已发货、已收货还是已结算；
- 单据只有页面快照，尚不能证明订货明细已进入库存事实。

### 3.2 商品报废

样本为一杯成品饮料报废，数量为 1，单位为空，原因使用自由文本而非标准原因码。

主要问题：

- 成品报废与物料报损是两种业务，不能混用同一库存扣减口径；
- 单位为空，无法换算数量与成本；
- 原因自由文本不能稳定聚合，应增加标准原因码，同时保留备注；
- 缺少照片、审批、金额、库存影响和 BOM 反冲策略；
- 如果成品报废不反冲物料，理论库存会偏高；如果重复反冲，也会造成二次扣减。

### 3.3 门店调拨

样本为两家门店之间的调拨，包含一种包材和一种原料。两行使用不同单位，但页面仍把行数量直接相加形成“调拨总数量”；两行商品编码均为空占位符。

主要问题：

- 两行商品编码均为 `-`，无法与库存物料主档稳定关联；
- 2 卷与 20 包直接汇总成“调拨总数量 22”，业务意义有限；
- 未看到调拨单号，无法用单号做幂等、防重复和追溯；
- “已完成”缺少调出、在途、到店、实收和差异处理状态；
- 缺少调出人、签收人、实收数量和短溢收证据；
- 金额未说明币种和价格来源。

### 3.4 共性根因

| 根因 | 直接后果 | 对 Demo 的影响 |
|---|---|---|
| 商品/物料编码缺失或不稳定 | 无法跨表关联 | 研判只能靠名称匹配，容易错配 |
| 采购单位、库存单位、销售单位未统一 | 数量不能直接计算 | 订货建议、调拨和理论库存不可信 |
| 状态过粗 | 不知道业务走到哪一步 | 工单无法自动判断下一步 |
| 订货、收货、调拨、报废缺少完整引用 | 同一动作可能重复计算 | V2 重算和审计不可靠 |
| 操作人是测试账号或为空 | 无法追责和回访 | 工单时间线失去生产意义 |
| 价格缺币种和生效口径 | 金额不可比较 | 暂不能展示真实成本和毛利 |
| 自由文本原因 | 无法聚类 | 总部看不到区域共性 |

## 4. 正式实施时先建立的数据门禁

### 4.1 必须有的稳定主键

- `tenant_id`
- `store_code`
- `sku_code`
- `material_code`
- `document_id/document_no`
- `document_line_id`
- `actor_id`
- `business_date` 与时区

名称只能用于展示，不能作为生产关联主键。

### 4.2 必须有的单位关系

每个物料至少保存：

- 库存基础单位；
- 订货单位；
- 包装规格；
- `order_unit_to_base_unit` 换算系数；
- 换算生效时间和版本；
- 是否允许小数。

任何缺失或冲突都应返回 `unavailable`，不能当成 0，也不能静默按 1:1 计算。

### 4.3 单据状态的最小统一模型

订货：

```text
草稿 → 已提交 → 待发货 → 在途 → 部分收货/已收货 → 已关闭
                       ↘ 取消/异常
```

调拨：

```text
草稿 → 已调出 → 在途 → 目标门店部分签收/全部签收 → 已关闭
                           ↘ 短货/多货/拒收
```

报损/报废：

```text
草稿 → 待确认 → 已确认并形成库存影响 → 已关闭
                     ↘ 驳回/冲销
```

“已完成”必须拆成可计算状态，或者在接入层明确映射规则。

### 4.4 数据质量状态

建议所有诊断输入统一携带：

- `verified`：主键、单位、期间和来源均通过；
- `estimated`：可以计算，但使用估算 BOM、价格或换算；
- `incomplete`：缺少部分记录；
- `conflict`：来源之间矛盾；
- `unavailable`：系统未接入或查询失败。

只有 `verified/estimated` 可进入建议计算；金额展示还需单独通过成本可信度门禁。

## 5. 建议订货 V0：先从消耗事实开始

### 5.1 产品定位

库存尚不可信时，不应直接声称“系统建议下单 X 箱”。第一版应叫“消耗与备货参考”，用于帮助门店理解近几周真实销售驱动的物料需求，并一键生成可编辑草稿。

V0 不自动扣减当前库存、不自动扣减在途、不自动提交订单。门店必须确认最终数量。

### 5.2 数据来源

优先使用：

```text
销售 SKU 明细 × 对应 BOM 版本 × 销售数量
→ 每日理论物料消耗
→ 7/14/28 日消耗趋势
```

如果 SKU 无 BOM 或 BOM 版本不完整：

- 销售仍保留；
- 缺失部分不进入物料消耗；
- 展示 BOM 覆盖率；
- 建议结果标记为 `incomplete`，不得补造消耗。

### 5.3 第一版指标

每个物料展示：

| 指标 | 口径 |
|---|---|
| 近 7 日理论消耗 | 最近 7 个完整营业日的销售 BOM 消耗 |
| 上一周理论消耗 | 上一个完整自然周或门店定义周 |
| 上上周理论消耗 | 用于计算周环比 |
| 周环比 | `(上周 - 上上周) / 上上周`；不是同比 |
| 近 28 日日均消耗 | 有效营业日消耗合计 / 有效营业日数 |
| 有效数据天数 | 销售、BOM 和营业状态均完整的天数 |
| BOM 覆盖率 | 已映射销售杯数 / 全部销售杯数 |
| 需求参考量 | 预测日均消耗 × 备货覆盖天数 |
| 订货单位换算 | 需求参考量 / 每订货单位基础数量，向上取整 |

去年同期数据存在且门店、商品、营业状态可比时，才增加“同比”。

### 5.4 V0 预测与建议公式

先采用可解释加权，不上复杂模型：

```text
最近 7 日日均 = 最近 7 个有效营业日消耗 / 有效天数
前 7 日日均   = 再往前 7 个有效营业日消耗 / 有效天数
较早 14 日日均 = 第 15～28 日有效消耗 / 有效天数

预测日均消耗 = 最近 7 日日均 × 50%
             + 前 7 日日均 × 30%
             + 较早 14 日日均 × 20%

需求参考量 = 预测日均消耗 × 备货覆盖天数
参考订货单位 = CEILING(需求参考量 / 每订货单位基础数量)
```

门店有效数据少于 14 天时，不给趋势结论，只展示近 7 日事实。有效数据少于 7 天时，不给订货参考量。

由于 V0 不可信任当前库存和在途，页面必须写“未扣减门店现存与在途，仅作为消耗参考”。如果门店愿意手工填写可用库存，可提供临时试算：

```text
试算订货量 = MAX(0, 需求参考量 - 门店确认可用库存)
```

### 5.5 后续 V1 公式

库存、在途和安全库存通过门禁后再升级：

```text
净需求量 = 预测日均消耗 × (采购提前期 + 复核周期)
         + 安全库存
         - 可信可用库存
         - 已确认在途

建议订货量 = MAX(0, 净需求量)
建议订货单位 = CEILING(建议订货量 / 包装换算)
```

V1 仍只生成草稿。促销、节假日、门店停业、新店爬坡和人工覆盖必须作为显式调整项，保留调整前后数量与原因。

## 6. 建议订货页面讨论稿

```text
订货管理
├─ Tab 1  消耗与备货参考
│  ├─ 门店 / 周期 / 物料分类筛选
│  ├─ 数据状态：有效天数、BOM 覆盖率、最新销售日
│  ├─ 物料表：7日、上周、上上周、周环比、28日日均、需求参考量
│  └─ 选择物料 → 生成订货草稿
├─ Tab 2  订货单
│  ├─ 草稿 / 已提交 / 待发货 / 在途 / 部分收货 / 已收货 / 异常
│  └─ 单据详情、价格快照、预计到货、关联收货和来源建议
└─ Tab 3  收货待办
   ├─ 今日预计到货
   ├─ 超期未收
   └─ 部分收货与差异
```

每条建议解释三件事：

1. 为什么出现；
2. 使用了哪些天的数据；
3. 哪些数据没有参与计算。

生成草稿时保存：`suggestion_id`、公式版本、计算输入、建议量、人工修改量和修改原因。后续才能评价建议是否有效。

## 7. 门店经营提醒：培养习惯而不是制造告警

### 7.1 门店首页只保留三层信息

```text
今天最重要（最多 1 条）
需要你处理（最多 3 条）
经营简报（每天 1 条，可展开）
```

立即打扰仅用于：

- 关键物料预计影响营业；
- 调拨/收货明确等待门店动作；
- 工单超时即将升级；
- 已处理问题重新触发。

其余销售波动、成本趋势、盘点习惯统一进入日报或周报。

### 7.2 排序原则

系统按四个维度排序，不向门店展示复杂分数：

1. 影响：是否影响营业、库存准确性或明确成本；
2. 紧迫：多久后会发生，SLA 是否接近；
3. 可行动：门店现在能否完成明确动作；
4. 可信度：证据是否完整，是否只是系统缺数据。

高影响但门店无法行动的系统问题，不推给门店，进入总部数据质量队列。

### 7.3 LLM 的职责

LLM 读取结构化事实后生成可接纳的自然语言：

```text
发生了什么
为什么值得现在处理
系统已经核对了什么
建议先做哪一步
完成后系统会如何验证
```

LLM 可以回答追问、解释业务语言、合并重复信息和生成草稿，但不能改变触发结果、自动定责、提交正式单据、修改库存或关闭工单。

### 7.4 用户反馈

门店除“立即处理”外，还应能选择：

- 稍后提醒；
- 今天无法处理；
- 与实际不符；
- 需要督导帮助；
- 已完成，等待系统验证。

反馈进入工单时间线，并用于后续评估提醒采纳率和误报率。

## 8. 总部运营：聚合问题而不是复制门店消息

总部首页建议分为四块：

```text
1. 今日需干预
   超时、门店拒绝、连续未恢复、关键物料风险

2. 共性问题
   多门店同物料、同供应商、同 BOM、同单位或同规则聚集

3. 执行与闭环
   按时完成率、V2 恢复率、重开率、门店采纳率

4. 数据质量
   缺编码、单位冲突、测试账号、占位库存、同步延迟、查询失败
```

默认先看区域/问题簇，点击后再进入门店工单。总部不应逐条处理全部门店提醒。

第一阶段可以直接聚合现有 D2/D1/S1/T2 和单据状态；销售、成本和毛利只有在完整数据门禁通过后才上线。

## 9. 现有 Demo 值得保留和调整的部分

### 9.1 保留

- V1/V2 双轨和规则版本；
- 首次/最新/历史研判快照；
- 工单关联订货、收货、调拨、盘点和流水；
- 业务动作后自动重算；
- 人工闭环、重开和升级门禁；
- 门店助手写入前人工确认；
- 订货与收货详情、部分收货和幂等确认。

### 9.2 优先调整

1. 建立 ICCPOS 导入适配层，不把外部“已完成”直接映射为内部已收货；
2. 订货明细增加物料编码、订货单位、换算、价格、币种和价格快照；
3. 收货与原订货逐行关联，记录短货、多货、破损和实收；
4. 调拨改成调出与目标门店签收两阶段；
5. 报废区分成品和物料，增加标准原因码；
6. 新增消耗与备货参考，不立即建设复杂自动补货；
7. 门店首页从“任务堆叠”改为最重要 1 条 + 待办 3 条；
8. 总部首页从异常列表改为干预、共性、闭环和数据质量四块；
9. 所有数字增加来源日期、口径和可信度；
10. 用功能开关或 `/v-next/` 预览，不影响现有演示主链。

### 9.3 暂缓

- 自动提交订货；
- 复杂机器学习预测；
- 真实支付网关、授信和自动对账；
- 在成本主数据不可信时展示精确毛利；
- 高频逐条推送所有异常；
- 将 LLM 作为规则裁决器或自动执行 Agent。

## 10. 建议验证顺序

### 阶段 A：数据映射样本

用本次三份单据加一份销售明细、一份 BOM、一份盘点和一份收货，完成：

- 门店、SKU、物料、单位和单据状态映射；
- 缺失、冲突、占位和测试数据门禁；
- 同一单据重复导入幂等测试。

### 阶段 B：建议订货 V0

为一个门店、5～10 个真实物料导入 28 天销售：

- 展示 7/14/28 日消耗；
- 计算周环比、有效天数和 BOM 覆盖率；
- 生成可编辑订货草稿；
- 保存系统建议与人工最终量；
- 不改库存、不自动提交。

### 阶段 C：门店经营提醒

只接三类高价值事件：

1. 关键库存风险；
2. 明确待收货/待签收/待盘点；
3. 处理结果或重开。

验证每店每天普通提醒不超过 3 条，同一问题原位更新。

### 阶段 D：总部聚合

至少使用 3 家门店模拟：

- 多店同物料异常聚合；
- 门店超时升级督导；
- 主数据问题进入总部治理；
- 原始工单、单据和 V2 结果可下钻。

### 阶段 E：库存与成本升级

在收货、在途、盘点、单位和价格通过门禁后，再上线：

- 可用库存与库存覆盖天数；
- 正式建议订货量；
- 缺货金额和积压金额；
- 理论物料毛利率；
- 安全库存与采购提前期动态参数。

## 11. 需要业务拍板的事项

1. 门店订货的业务周从周一还是其他日期开始；
2. V0 默认备货覆盖天数；
3. 真实订货单位与基础库存单位换算由谁维护；
4. ICCPOS “已完成”在订货、调拨和报废中分别代表什么；
5. 成品报废是否按 BOM 反冲物料；
6. 门店调拨是否必须由目标门店确认实收；
7. 门店每天普通提醒上限是否采用 3 条；
8. 督导的区域和门店责任映射；
9. 采购价格采用订货价、标准成本还是移动平均成本；
10. 第一家试点门店及 5～10 个真实物料范围。

## 12. 下一步建议
