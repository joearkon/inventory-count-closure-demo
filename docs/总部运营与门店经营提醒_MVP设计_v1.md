# 总部运营与门店经营提醒 MVP 设计 v1

> 状态：设计基线，供 Codex 与飞书/豆包工作侧共同维护  
> 更新时间：2026-09-17  
> 适用范围：库存研判、跟进工单、门店经营提醒、督导介入和总部运营  
> 关联实现：《库存研判闭环设计_v1.md》

## 1. 结论与定位

门店端不应建设一个独立的“异常中心”，而应建设“门店经营提醒”；总部端不应再建设一套平行工单，而应在“总部运营”中聚合门店、区域和规则维度的风险与执行状态。

三端共用同一套异常事实、工单、V2 研判快照和业务单据：

```text
规则或经营信号
→ 形成/更新唯一业务工单
→ 按角色生成提醒视图
→ 门店、督导或总部执行动作
→ 收货/调拨/盘点/订货等业务事实更新
→ 自动运行 V2 重算
→ 更新提醒结论
→ 人工确认闭环或升级
```

核心原则：

1. **工单是业务事实，提醒是触达方式。** 提醒不得复制和维护另一套异常结论。
2. **V2 重算是系统验证，人工结论是最终业务决策。** “已读”“我知道了”“已处理”都不能直接关闭工单。
3. **同一数据、同一规则、不同视角。** 门店看“会不会影响营业、现在做什么”；督导看“哪些门店需要介入”；总部看“是否为区域性、主数据或供应链问题”。
4. **规则先判断，LLM 后解释。** MVP 的触发、抑制、关闭门禁继续由结构化规则执行；LLM 可用于摘要、问答和行动建议，不得自动定责或绕过人工确认。
5. **站内状态先跑通，再扩展飞书渠道。** 飞书是投递通道，不是第二套业务系统。

## 2. 设计依据

本设计吸收并校准以下资料：

- `references/architecture.md`：同一套数据、知识库、模型和 Skill，面向加盟商与总部形成不同视角；建议包含日报、实时告警、周报和事件通知。
- `references/mvp-package/knowhow/v2/store_operations_anomaly.md`：门店经营异常覆盖销售、盘点、客流、客单和服务/财务五个维度；MVP 默认采用近 3 日窗口和五档研判。
- `references/mvp-package/knowhow/v2/store_operations_scenarios_v1.md`：ST-1 至 ST-5 的触发条件、三角色响应与验收标准。
- `references/mvp-package/deliverables/v1/response_action_map.json`：D2/D1/S1/T2 的判定档、责任角色、动作、SLA、反馈要求和升级路径。
- `docs/库存研判闭环设计_v1.md`：当前已实现的首次 V2 快照、业务动作关联、自动重算、前后对比、关闭门禁和后续异常发现。

豆包资料中的“所有库存问题都翻译成多少钱”“点击已处理后列表移除”等表述，在本 MVP 中增加可信度和关闭门禁：成本不可信时不展示金额；状态只能由真实业务动作、V2 重算和人工结论共同推进。

## 3. 目标与边界

### 3.1 MVP 目标

- 门店每天只看到最重要且能执行的经营事项，而不是技术枚举和重复告警。
- 督导能看到待介入、即将超时、门店拒绝或连续未解决的事项。
- 总部能聚合同类异常，识别单店问题、区域共性、主数据问题和供应链问题。
- 每条提醒都可追溯到来源信号、规则版本、工单、业务单据、V2 重算和人工结论。
- 同一异常在重算、刷新和多渠道投递时不会重复轰炸。
- 先用现有库存 D2/D1/S1/T2 跑通，再逐步接入销售、盘点执行、客单和服务经营信号。

### 3.2 MVP 不做

- 不因单日正常波动自动创建经营工单。
- 不让 LLM 自动定责、改库存、提交正式单据或关闭工单。
- 不在成本、单位或数量证据不可信时展示精确损失金额。
- 不为站内消息、飞书卡片和邮件分别维护业务状态。
- 不在 MVP 阶段上向量数据库；规则、动作映射和文案模板继续采用版本化 JSON/Markdown 精确查表。
- 不自动判断员工个人责任、供应商责任或口味质量问题。

## 4. 三角色视角

| 角色 | 核心问题 | 默认内容 | 可执行动作 | 升级条件 |
|---|---|---|---|---|
| 门店/加盟商 | 是否影响营业或赚钱？我现在做什么？ | 当前影响、关键数字、建议动作、截止时间 | 查看证据、收货、盘点、订货、确认调拨、补录说明 | 超时、拒绝、证据冲突、连续未恢复 |
| 区域督导 | 哪些门店需要介入？门店是否执行？ | 区域门店风险、SLA、门店反馈、重算结果 | 复核、派单、现场协助、升级总部 | 门店超时、连续两次未关闭、多项异常叠加 |
| 总部运营 | 是单店问题还是系统性问题？如何管控？ | 多门店聚合、规则分布、主数据/供应链共性、闭环质量 | 调整政策、治理主数据、批量派单、确认例外 | 多门店同物料、规则误报聚集、供应链或主数据异常 |

三个视角使用同一 `work_order_id`。角色差异通过 `audience`、展示字段、动作权限和升级策略表达，不复制异常记录。

## 5. 产品结构

### 5.1 门店端：经营提醒

门店移动端底部增加“消息/提醒”入口和未读角标；首页“今日最重要”只保留 1～3 条，完整历史进入提醒列表。

每张卡片最多包含：

1. 发生了什么；
2. 对营业/库存/成本可能有什么影响；
3. 系统已核对的证据；
4. 当前建议动作和截止时间；
5. `立即处理`、`查看证据`、`稍后提醒`等按钮。

“我知道了”只更新已查看/已确认状态，不代表问题解决。

### 5.2 督导端：区域待介入

在总部运营中提供督导视图：

- 按区域、门店、优先级、SLA、状态筛选；
- 默认突出门店超时、连续未恢复、证据冲突和多项异常叠加；
- 可下钻同一工单的首次/最新 V2、门店操作、单据和人工记录；
- 可派发现场复核、退回补证据或升级总部。

### 5.3 总部端：运营聚合

总部运营不逐条阅读所有门店消息，而看聚合结论：

- 今日新增、处理中、超时、已恢复和重开数量；
- 多门店同物料/同规则聚集；
- 门店采纳率、按时完成率、V2 恢复率、重开率；
- 主数据治理、供应链和规则误判清单；
- 可下钻到门店工单和原始证据。

## 6. 消息分类

| 分类 | 典型内容 | 门店触达 | 督导/总部触达 | MVP 频率上限 |
|---|---|---|---|---|
| 立即处理 | 严重负库存、关键物料预计断货、调拨待签收、工单重开 | 即时卡片 + 首页置顶 | 高风险同步 | 同一问题冷却期内仅更新原卡 |
| 今日待办 | 待盘点、待收货、待补证据、即将到期 | 消息中心 + 每日汇总 | 仅在临近 SLA/超时出现 | 每类每日最多 1 次汇总 |
| 经营关注 | 连续低销、客单下滑、盘点异常率、损耗趋势 | 日报/周报，不做单日轰炸 | 区域聚合 | 日报 1 次，周报 1 次 |
| 处理结果 | 已恢复、仍未解决、发现后续异常、总部退回/确认 | 事件触发 | 同步状态 | 每次状态跃迁 1 条 |
| 系统/数据 | 同步延迟、查询失败、历史不完整 | 仅当门店可补证据时触达 | 默认进入总部数据质量队列 | 同源故障合并 |

## 7. 触发、抑制、去重与频率

### 7.1 触发策略

- `confirmed`：存在明确可执行动作时创建/更新工单并触达责任角色。
- `suspect`：进入消息中心；只有需要门店或督导核实时才强提醒。
- `insufficient`：仅向能够补齐证据的角色发出任务；纯系统延迟先自动重试。
- `pending` / `pending_count`：监控或等待盘点，不强提醒；超过等待窗口再升级。
- `excluded`：归档，不推送。
- 工单 SLA 临近、超时、V2 结果改变、关闭、重开或升级：产生状态型提醒。

`response_action_map.json` 在 MVP 中作为动作选择和 SLA 的结构化来源，首批采用以下映射：

| 库存规则/判定 | 首要责任 | 建议动作 | SLA/升级 |
|---|---|---|---|
| INV-D2 `confirmed` | 门店，系统负责触达 | 核对流水并补录入库/收货；必要时盘点 | 1h 未响应通知督导，2h 未补录转现场核查 |
| INV-D2 `suspect` | 督导 | 复核流水、单据号和门店反馈 | 4h 未复核转总部派单 |
| INV-D2 `insufficient` | 系统 | 等待数据并自动重跑 | 默认 30 分钟，不打扰门店 |
| INV-D1 `confirmed` | 门店 + 督导 | 完整盘点、复核理论与实盘差异 | 12～24h，未完成由督导介入 |
| INV-S1 `confirmed` | 门店 | 创建采购草稿或调拨申请 | 4～24h，按物料紧急程度升级 |
| INV-T2 `confirmed/suspect` | 门店或督导 | 补录入库、复核销量/入库/BOM | 12～24h，未复核转总部研判 |

动作映射只给出默认责任与时限，工单中的事实、物料分类和最新 V2 结果仍是具体文案与动作排序的依据。

### 7.2 抑制策略

以下情况不产生门店即时提醒：

- 单日销售或客单波动，尚未达到连续窗口；
- 门店停业、节假日、促销、新品或已知外部事件已解释；
- 数据延迟且系统仍在自动重试窗口内；
- 最新 V2 已恢复且无后续异常；
- 相同问题已存在有效工单，且没有新的状态变化；
- 门店无权或无法补齐缺失证据；此类进入总部数据质量队列。

### 7.3 去重与合并

建议业务去重键：

```text
tenant_id + store_code + subject_type + subject_id
+ rule_namespace + rule_code + business_window
```

- 同一门店、同一物料、同一规则、同一营业窗口只保留一个活动工单和一条聚合提醒。
- V2 重算只追加 `diagnosis_run_id` 并更新提醒摘要，不新建提醒。
- 渠道投递使用独立 `delivery_id`；站内、飞书和邮件失败不改变业务状态。
- D2 恢复后发现 D1 时属于新的规则问题：保留 D2 已恢复结论，并在原工单提示后续 D1；由人工选择建立后续工单，不能把两个异常覆盖成一个。
- 多门店同物料同时触发时，总部端可合并为区域事件；门店端仍各自引用本店工单。

### 7.4 频率与升级

- 即时提醒：同一活动问题默认 30 分钟冷却；仅在优先级上升、SLA 超时、结论变化或被重新打开时突破冷却。
- 门店日报：每天 1 次，汇总销售、库存风险、待处理动作。
- 门店周报：每周 1 次，展示趋势和已闭环结果。
- 督导：首次需介入时 1 次；SLA 超时再提醒；不随每次轮询重复发送。
- 连续两次 SLA 超时或两次 V2 重算仍未恢复，升级上一级角色。

## 8. 消息状态机

业务提醒状态与渠道投递状态必须分开。

### 8.1 业务提醒状态

```text
draft
→ eligible
→ active
→ viewed
→ acknowledged
→ in_progress
→ resolved
```

旁路状态：

- `suppressed`：命中抑制策略；保留原因与规则版本；
- `expired`：业务窗口结束且没有继续处理价值；
- `escalated`：原责任角色未完成，已升级但原记录仍保留；
- `reopened`：原工单关闭后再次触发或人工确认仍未解决。

状态门禁：

- `viewed` / `acknowledged` 只表示阅读和接收，不改变工单研判状态；
- `in_progress` 必须有人工记录或关联业务动作；
- `resolved` 必须引用工单的合法闭环结论；
- V2 仍触发时不得以“已恢复”进入 `resolved`；只能接受例外、规则误判、主数据问题或继续处理。

### 8.2 渠道投递状态

```text
queued → sending → delivered → opened
                 ↘ failed → retrying → delivered/dead_letter
```

投递失败不创建第二条业务提醒；重试必须沿用 `notification_id + channel + recipient_id` 的幂等键。

## 9. 与工单、业务动作和 V2 重算的关系

```text
异常信号/经营信号
  ↓
首次 V2 快照（来源、计算、证据、缺口、规则版本）
  ↓
工单（唯一业务事实）
  ↓
提醒投递（门店/督导/总部不同视图）
  ↓
盘点、收货、调拨、订货、报损或人工核查
  ↓
业务单据确认后自动 V2 重算
  ↓
┌─ 已恢复：提醒更新为“问题已恢复”，等待人工结论
├─ 仍触发：提醒更新下一步，必要时升级
└─ 新异常：保留原结论，提示建立后续工单
  ↓
人工填写最终原因、解决方式、操作人、门店采纳和总部确认
  ↓
工单关闭；提醒同步 resolved
```

### 9.1 已跑通的示范链路

黑糖珍珠 D2 工单 `OPT-2FBCCD16` 已完成：

- 处理前理论库存 `-1,090g`；
- 关联紧急订货、收货和入库流水；
- 收货 `2,000g` 后 V2 自动重算为 `910g`，D2 不再触发；
- 人工填写最终原因和解决方式后关闭；
- 系统继续发现实盘 `800g` 与理论 `910g` 的 D1 差异，并作为后续问题提示。

该链路应成为提醒 MVP 的第一条验收主线：门店收到 D2 → 进入工单 → 执行动作 → 收到“D2 已恢复但发现 D1 差异” → 人工决定是否建立后续工单。

## 10. 成本与经营金额可信度

豆包文档提出“数字即成本”，方向正确，但金额必须受可信度门禁约束。

只有同时满足以下条件时，提醒才展示精确金额：

1. 存在有效采购成本、标准成本或移动平均成本；
2. 成本有币种和生效日期；
3. 基础单位、采购单位和换算系数有效；
4. 异常数量不是证据不足、查询失败或单位冲突状态；
5. 成本口径与展示对象一致，例如“潜在缺货销售影响”不能伪装成“实际损失”。

建议 `cost_confidence`：

| 值 | 展示策略 |
|---|---|
| `verified` | 展示金额、币种、成本口径和计算式 |
| `estimated` | 显示“估算”，同时展示区间和假设 |
| `unavailable` | 不展示金额，改为可售天数、影响 SKU 数、缺口数量等 |

没有可信成本时，推荐文案：“可能影响 3 个高销量 SKU”“预计可售不足 1 天”“待成本主数据完善后计算金额”，禁止显示看似精确的损失金额。

## 11. 规则命名空间

现有库存规则的 `S1` 表示“安全库存预警”，豆包门店运营文档的 `S1` 表示“销售异常”，存在冲突。MVP 必须引入命名空间：

| 展示/接口名称 | 含义 |
|---|---|
| `INV-D2` | 库存理论负库存 |
| `INV-D1` | 库存理论与实盘差异 |
| `INV-S1` | 库存安全库存预警 |
| `INV-T2` | 库存销入比异常 |
| `OPS-S1` | 门店销售异常 |
| `OPS-S2` | 门店盘点执行异常 |
| `OPS-S3` | 门店客流异常 |
| `OPS-S4` | 门店客单价异常 |
| `OPS-S5` | 门店服务/财务异常 |

数据契约中禁止只保存裸 `S1`；必须同时保存 `rule_namespace` 和 `rule_code`。旧数据可显示回退，但新写入必须使用完整命名。

## 12. 当前已经实现

### 12.1 库存研判与工单闭环

- D2/D1/S1/T2 规则研判及 V2 影子结果；
- 首次快照和每次重算快照；
- 证据、缺失证据、计算公式、规则版本和建议动作；
- 工单关联盘点、调拨、订货、收货、报损和库存流水；
- 收货确认、调拨签收和盘点完成后的自动重算；
- “库存修正与验证”前后变化展示；
- 人工闭环表单、关闭门禁、重开和升级；
- 原规则恢复后识别同物料后续异常。

### 12.2 门店执行入口

- 门店移动端今日待办和门店助手；
- 查询库存、多物料查询、盘点、收货、订货、报损和调拨；
- 写入前人工确认；
- 中、英、印尼语输入基础能力；
- 工单动作携带门店、物料、日期和来源工单上下文。

### 12.3 现有机器人推送基础

- 总部“飞书机器人推送配置”页面；
- 飞书群机器人 Webhook 与签名支持；
- 实时库存异常和运营日报模板；
- 负库存、安全库存和调拨/数据异常开关；
- 同一研判冷却时间、日报时间和内容范围配置；

## 15. 分阶段验收案例

### 阶段 0：现有能力保护

- 飞书预览在未配置 Webhook 时返回明确失败原因；
- 冷却和日报去重不重复发送；
- D1/D2/S1/T2 工单仍能重算、关闭、重开和升级；
- 提醒代码不得改变库存或绕过写入确认。

### 阶段 1：库存提醒 MVP

以黑糖珍珠 D2 为主案例：

1. D2 首次触发，只生成一个活动工单和一条门店提醒；
2. 门店打开提醒，工单状态不因“已查看”改变；
3. 门店创建订货/收货并确认，系统自动 V2 重算；
4. 提醒原位更新为“D2 已恢复”，不新增重复提醒；
5. 系统提示新的 D1 差异，保留两类问题的边界；
6. 人工填写闭环结论后，提醒进入 `resolved`；
7. 工单重开时提醒进入 `reopened` 并通知当前责任角色。

验收补充：同时覆盖 D1 盘点差异、INV-S1 补货、T2 销入比各一条，验证动作映射与 SLA。

### 阶段 2：督导与总部

- 门店超时后仅产生一次督导升级提醒；
- 督导能看到门店反馈、业务单据和最新 V2；
- 三家门店同物料异常可在总部聚合，但门店工单仍独立；
- 主数据问题转总部治理，原工单等待治理后复算；
- 总部列表中的“已处理”必须来自合法闭环，不能人工隐藏未解决工单。

### 阶段 3：经营提醒

按资料中的场景验收：

- ST-2 近 3 日未盘点：优先接入，门店补盘后自动刷新；
- ST-1 近 3 日低销：排除停业、节假日、同期同型均低和数据延迟；
- ST-4 客单价下滑：排除促销、新品和大单效应；
- ST-3 盘点异常率高：新店首月排除，督导可派单；
- ST-5 退货率与客诉：仅在真实数据源接入后启用。

所有场景共同验证：中文、英文、印尼语；单日异常不推送；站内与飞书状态一致；门店确认、督导介入、总部下钻链路完整。

## 16. MVP 完成定义

满足以下条件，经营提醒 MVP 才可认为完成：

- 一个业务问题只有一个活动工单，允许多角色、多渠道视图；
- 门店能在 3 秒内理解影响和下一步，动作入口带完整上下文；
- 提醒已读、业务执行、V2 恢复和人工关闭四种状态互不混淆；
- 重算不会重复轰炸，状态变化会及时更新；
- 督导超时升级与总部聚合可追溯；
- 所有展示数字均能回到证据和计算口径；
- 成本不可信时不显示伪精确金额；
- INV/OPS 命名空间消除 S1 冲突；
- 黑糖珍珠 D2 主链和至少 D1、INV-S1、T2 三条补充链路自动回归通过。

## 17. 建议实施顺序

1. 先定义并冻结通知数据契约与状态机；
2. 为现有工单事件增加通知投影，不改研判规则；
3. 建设门店站内提醒列表和角标；
4. 建设督导/总部统一运营视图；
5. 接入 SLA、抑制、去重和升级；
6. 将现有飞书机器人迁移为统一通知的一个 delivery adapter；
7. 用 D2 全链路回归；
8. 再接 `OPS-S2` 未盘点和 `OPS-S1` 连续低销；
9. 数据可信后再扩展成本金额、客单、客诉和 LLM 个性化解释。
